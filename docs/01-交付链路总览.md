# 交付链路总览：一次代码变更的完整旅程

这份文档只回答一个问题：**从我改完代码，到集群里真的在跑这份代码，中间发生了什么。**

如果只看目录结构，你很可能会把 `Dockerfile`、`deploy/`、`gitops/`、`.github/workflows/ci.yml` 当成一堆并列的配置文件。它们不是并列的——它们分属两条**节奏不同、目的不同、信任边界不同**的循环。把这两条循环分清楚，后面每一份清单为什么长成那样就都能自己推出来。

---

## 一、两条循环，两种节奏

| | 内循环（开发） | 外循环（交付） |
|---|---|---|
| 触发者 | 开发者敲命令 | `git push` |
| 追求 | 秒级反馈，改完就看到 | 可追溯、可回滚、无人值守 |
| 镜像地址 | `localhost:5001/cnlab:dev` | `ghcr.io/am-okalin/cnlab:sha-f24b9a4` |
| tag 性质 | **可变**（每次覆盖同一个 `:dev`） | **不可变**（每个 commit 一个 sha） |
| `imagePullPolicy` | `Always`（必须） | `IfNotPresent`（可以） |
| 谁让 Pod 换掉 | 你，`kubectl rollout restart` | ArgoCD，因为它看到 git 里的 tag 变了 |
| 需要 git 吗 | **不需要** | 必须 |
| 需要 CI 吗 | 不需要 | 必须 |
| 失败的影响面 | 只有你这台机器 | staging / prod |

一句话概括区别：**内循环优化的是"我知道我改对了没有"，外循环优化的是"三个月后我能说清线上跑的是哪个 commit"。** 这两个目标会互相伤害——可变 tag 让内循环快，但让外循环无法追溯；所以它们必须是两条路，而不是一条路上加开关。

## 三、内循环：为什么它必须快，以及它为什么需要 `rollout restart`

### 完整命令序列

```bash
make image-push-local
kubectl --context kind-cnlab -n cnlab-dev rollout restart deploy/cnlab
kubectl --context kind-cnlab -n cnlab-dev rollout status  deploy/cnlab
kubectl --context kind-cnlab -n cnlab-dev logs -l app.kubernetes.io/name=cnlab -f --tail=20
```

### 为什么 `make deploy-dev` 在这里不够用

README 的快速开始里写的是 `make image-push-local && make deploy-dev`。那套顺序在**第一次**部署时是对的：Deployment 还不存在，`kubectl apply` 会创建它，创建过程必然拉镜像。

但从第二次改代码开始，`make deploy-dev` 就变成了一个空操作，原因是清单**一个字节都没变**：

- 镜像地址还是 `localhost:5001/cnlab:dev`（tag 是固定的 `:dev`，不随代码变）
- ConfigMap 的内容没变，所以 `cnlab-config-<hash>` 这个哈希后缀也没变
- 于是 Pod 模板的哈希不变 → Deployment 不生成新的 ReplicaSet → 现有 Pod 原样不动

新镜像确实躺在本地仓库里了，但 **K8s 没有任何理由去发现这件事**。这就是可变 tag 的代价：清单层面看不出"有新东西"。所以内循环的最后一步必须是一次显式的 `rollout restart`——它给 Pod 模板打一个时间戳注解，强行制造一次滚动更新，配合 `imagePullPolicy: Always` 让节点重新去仓库拉 `:dev`。

> 顺带一个可以补的缺口：本项目没有 `make rollout-restart` 这个目标，而内循环每轮都要用一次。这是 Makefile 里最值得加的一行。

### 为什么 `imagePullPolicy` 在 dev 里必须是 `Always`

看 `deploy/overlays/dev/patch-dev.yaml`：dev overlay 只做了一件事——把 `imagePullPolicy` 从 base 的 `IfNotPresent` 改成 `Always`。这一行是整个内循环能否工作的开关。

去掉它会怎样：节点上已经有 `cnlab:dev` 这个 tag 了，containerd 认为"本地有，不用拉"，于是 `rollout restart` 起了新 Pod，跑的却是**旧二进制**。现象是改了日志、改了返回值，重新部署后完全看不到变化，你会开始怀疑 Dockerfile、怀疑 buildx、怀疑缓存——而真正的原因只是一行 `IfNotPresent`。这是本地 kind + 可变 tag 最经典的坑。

生产环境反过来：tag 不可变（`sha-f24b9a4`），用 `IfNotPresent` 既不会踩这个坑，又省一次网络往返。

### 这个循环里没有 git，这就是重点

`main.go` 随便改、随便提交本地 commit，甚至完全不做版本控制，内循环照样转。它的价值在于**把"验证想法"和"记录历史"这两件事解耦**。一旦你为了看一眼效果而必须先 commit、先 push、先等流水线，内循环就死了，你就会开始在生产上直接改——那才是真正的风险。

## 四、外循环：四个 job，和一个不是 deploy 的 job

看 `.github/workflows/ci.yml`，四个 job 的依赖关系是：

```
quality ──► image ──► gitops
manifests（独立，与 quality 并行）
```

实测一次完整运行（第二次跑，全绿）的耗时：

| job | 耗时 | 在做什么 |
|---|---|---|
| 质量门 `quality` | 18s | `gofmt -l`、`go vet`、`golangci-lint v2.12.2`、`go test -race`、覆盖率 |
| 校验清单 `manifests` | 24s | 渲染全部 overlay → `kubeconform -strict` 校验 schema |
| 构建镜像 `image` | 51s | buildx 多架构构建，推 GHCR |
| 更新 staging 期望状态 `gitops` | 12s | `kustomize edit set image` → commit → push |

`manifests` 不依赖 `quality`，所以它和 `quality` 并行；`image` 必须等 `quality` 绿；`gitops` 必须等 `image`。按各 job 耗时推算，墙钟时间约 80 秒。

### 关键点 1：这里没有 `kubectl apply`，而且不该有

`.github/workflows/ci.yml` 顶部的注释把这件事说得很直接：**CI 的职责到"把镜像推进仓库、把新 tag 写回期望状态"就结束了**。真正让集群发生变化的是集群里的 ArgoCD。

如果给 CI 加上 `kubectl apply`，你会立刻需要付出这些代价：

- 集群的 kubeconfig（或一个高权限 ServiceAccount token）必须以 secret 的形式存进 GitHub。**集群凭证开始散落在 CI 系统里**，此后每加一个 CI 平台就多一份副本。
- 谁能在仓库里改 workflow，谁就能拿到集群权限。代码仓库的权限模型被悄悄提升成了集群的权限模型。
- 网络方向反转：CI（公网）需要能连到集群 API Server（通常在内网）。于是你要么暴露 API Server，要么跑 self-hosted runner。
- 漂移无人管：CI 只管"我推的那一下"，之后有人手动改了集群，git 里看不出来。

pull 式（ArgoCD 从 git 拉）把上面四条全部消掉：CI 只需要能写 git，集群只主动往外拉。

### 关键点 2：`manifests` 这个 job 值得单独存在

`kustomize build` 只保证"能渲染成 YAML"。它完全不管字段名拼没拼错、字段放没放对层级、`apiVersion` 存不存在。所以 `manifests` job 在渲染之后又跑了一遍 `kubeconform -strict`，拿官方 JSON Schema 做离线校验。

实测结果是 dev 5 个资源、staging 5 个资源、prod 6 个资源（prod 多一个 PodDisruptionBudget），全部 `Valid`、`0 Invalid`。

这一步的价值在于**把"清单写坏"的成本从"集群里出问题"降到"PR 上一条红叉"**。没有它，写错一个 `terminationGracePeriod` 这种字段，`kubectl apply` 会**静默忽略**（client-side 不做未知字段校验），你以为改了，其实没改。

### 关键点 3：tag 是手算的，不是 `metadata-action` 挑的

`ci.yml` 里有一段专门手写 shell 算 tag：

```bash
if [[ "${GITHUB_REF_TYPE}" == "tag" ]]; then
  echo "value=${GITHUB_REF_NAME}" >> "$GITHUB_OUTPUT"
else
  echo "value=sha-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"
fi
```

注释里写明了原因：`docker/metadata-action` 的 `version` 输出会按优先级挑一个 tag，而 `type=raw,value=latest` 的优先级高于 `type=sha`。用它去写期望状态，会把 `latest` 写进 GitOps 仓库——正好废掉"用不可变 tag 才能回答线上跑的是哪份代码"这个前提。

历史上这个坑真实发生过：`git log` 里有一条 `chore(gitops): staging -> latest [skip ci]`，正是这条路径把 `latest` 提交进了 overlay，随后被 `fix(ci)` 修掉。

### 关键点 4：`gitops` job 的提交是幂等的，也是有意的

```bash
git add deploy/overlays/staging/kustomization.yaml
if git diff --cached --quiet; then
  echo "期望状态无变化，跳过提交"
  exit 0
fi
git commit -m "chore(gitops): staging -> sha-xxxxxxx [skip ci]"
```

两件事值得注意：

- **幂等保护**：tag 没变就什么都不做。否则每次 CI 都会产生一个空提交连锁。
- **`[skip ci]` 是承重的**：这个提交改的是 `deploy/overlays/staging/kustomization.yaml`，而 workflow 的 `paths-ignore` 只忽略 `docs/**` 和 `**/*.md`——`.yaml` 不在忽略范围内。也就是说，**如果没有 `[skip ci]`，这个写回提交会立刻触发一次新的 CI**，形成自激循环。`paths-ignore` 救不了你，`[skip ci]` 才救得了你。

### 关键点 5：tag 构建不走这条路

`gitops` job 带了 `if: github.ref == 'refs/heads/main'`。推 `v*` tag 时它被跳过——打 tag 是发布动作，生产上线要人工提升，不该由自动路径完成。

## 五、为什么两个循环的镜像地址结构必须一致

这是整套设计里最容易被忽略、但收益最大的一条。

```yaml
# deploy/overlays/dev/kustomization.yaml
images:
  - name: cnlab
    newName: localhost:5001/cnlab     # ← 只有 registry 前缀不同
    newTag: dev                       # ← tag 是可变值

# deploy/overlays/staging/kustomization.yaml
images:
  - name: cnlab
    newName: ghcr.io/am-okalin/cnlab  # ← 只有 registry 前缀不同
    newTag: sha-f24b9a4               # ← tag 由 CI 写入

# deploy/overlays/prod/kustomization.yaml
images:
  - name: cnlab
    newName: ghcr.io/am-okalin/cnlab
    newTag: v0.1.0                    # ← 不可变语义化版本
```

三个 overlay 用的都是 `<registry>/<image-name>` 这个同一个结构。`deploy/base/deployment.yaml` 里那一行 `image: cnlab:dev` 是故意留的**不完整值**——它的存在逼着每个 overlay 必须显式声明"用哪个仓库、哪个 tag"，否则渲染结果会指向一个不存在的镜像。

`hack/kind-up.sh` 顶部把这条理由写得很清楚：正因为本地仓库让 dev 的地址结构和生产一致，Kustomize 的 `images` 转换器就只需要改 registry 前缀和 tag。**如果改用 `kind load` 把镜像直接灌进节点，本地环境就会走一条生产根本不存在的特殊路径**——那么你在本地验证过的一切，都不能证明生产上行得通。

具体来说，一致性带来两个直接好处：

1. **overlay 的 diff 是可读的**。`kubectl diff` 或 `argocd app diff` 出来的差异，就是"registry 前缀 + tag"这两处，没有别的噪音。
2. **内循环踩过的坑在生产同样会踩**。`localhost:5001` 的解析依赖 `kind/cluster.yaml` 里的 containerd registry mirror 配置；而 `imagePullPolicy`、探针、优雅下线这些真正难的东西，两套环境走的是同一条代码路径。

## 六、每个环节的信任边界

这是"为什么 CI 里没有 deploy"的另一种表述方式。把每个角色**需要**什么凭证和**绝不**需要什么列出来，安全模型就一目了然了：

| 角色 | 需要 | 明确不需要 | 为什么 |
|---|---|---|---|
| 开发者（内循环） | Docker（推 `localhost:5001`）、`kubectl`（context `kind-cnlab`） | git 写权限 | 内循环的全部意义就是"不碰 git" |
| Actions `quality` | `contents: read` | 集群凭证 | 只跑检查和测试 |
| Actions `manifests` | `contents: read` | 集群凭证 | 只渲染 YAML + 离线 schema 校验 |
| Actions `image` | `contents: read` + `packages: write` | 集群凭证 | 只推镜像 |
| Actions `gitops` | `contents: write` | **集群凭证** | 它只写 git。注意 `permissions` 是按 job 声明的，默认全局只有 `contents: read` |
| ArgoCD（集群内） | git 读、集群内 RBAC | **git 写权限** | 只读期望状态；"能写集群"是它本来就有的能力，不需要额外给 |
| 镜像拉取 | 私有仓库时需要 pull 凭证 | — | 当前三套 overlay 里都**没有** `imagePullSecrets`，说明设计前提是 GHCR 包公开 |

边界的两条结论：

- **集群凭证从不离开集群。** 这条线上没有任何一处需要把 kubeconfig 或集群 token 交出去。CI 的攻击面被限制在"能写这个仓库"。
- **"能改 git"就等于"能改集群的期望状态"。** 这是 pull 式模型的固有属性，不是缺陷，但它把风险点转移了：谁能合并到 `main`，谁就间接决定了集群跑什么。所以 `gitops/apps/` 里的 prod Application 刻意关掉了自动同步——见 `gitops/examples/cnlab-prod.yaml`。

> 值得留意的一个缺口：`deploy/overlays/*/kustomization.yaml` 里的 `images.newName` 是一个纯文本字段。**任何能改 git 的人，都能让集群去拉任意仓库的任意镜像。** 目前没有任何准入校验能拦住这一步。这是挑战练习里"供应链安全 + 准入校验"要解决的问题。

## 七、"我改了 X，会发生什么"

| 我改了… | 谁会发现 | 多久生效 | 集群里发生什么 |
|---|---|---|---|
| `main.go`（不 push） | 只有你 | 几十秒 | `make image-push-local` + `rollout restart` 后 dev Pod 换新二进制。**不需要 git，不需要 CI** |
| `main.go` 并 push 到 `main` | Actions → ArgoCD | 约 80s 流水线 + ArgoCD 检测 | `staging/kustomization.yaml` 的 `newTag` 变成 `sha-新值`；staging Pod 换成新镜像。**全程没人敲部署命令** |
| `deploy/overlays/dev/` 里的配置（只改工作区） | 只有你 | 立即 | `make deploy-dev` 生效。若改的是 ConfigMap，哈希后缀变化 → Pod 模板变化 → 自动滚动更新，**不需要 `rollout restart`** |
| 同上，但 push 到 `main` | ArgoCD（dev Application 自动同步） | 秒级到 3 分钟 | ⚠️ 同一时刻本地 `make deploy-dev` 的改动会被 ArgoCD 的 `selfHeal` 纠回 git 的状态 |
| `deploy/overlays/staging/` 的 `newTag`（手动改并 push） | ArgoCD（staging 自动同步） | 秒级到 3 分钟 | staging 换成你写的 tag。⚠️ 下一次 CI 在 `main` 上跑 `gitops` job 时，会用新算出的 sha 覆盖它 |
| `deploy/base/*` | 三个环境**全部** | 取决于各环境谁在同步 | base 被每个 overlay 合并，dev/staging 由 ArgoCD 自动同步；prod 只有在你手动 `apply -f gitops/examples/cnlab-prod.yaml` 之后才会动 |
| `kind/cluster.yaml` | **没有人** | 只有 `make kind-down && make kind-up` 之后 | 现有集群完全不变。它是 `kind create cluster` 的输入，不是集群的期望状态 |
| `gitops/apps/*.yaml` 并 push | `cnlab-root`（`directory.recurse: true`） | 秒级到 3 分钟 | 新增/删除一个环境的 Application。**这就是"加一个环境不用碰集群"的杠杆** |
| `hack/*.sh`、`Makefile` | 没有人 | 你下次敲这些命令时 | 对集群零影响 |
| `.github/workflows/ci.yml` 并 push | GitHub Actions | 下次运行 | 对集群零直接影响——除非你动了 `gitops` job |

关于"秒级到 3 分钟"这个区间：ArgoCD 默认的 `timeout.reconciliation` 是 3 分钟，所以**没有配 git webhook 时，git 变更最坏要等一个轮询周期**。而实测的"4 秒纠回漂移"走的是另一条路径——集群内的 watch 事件，与 git 轮询无关。这两个数字不矛盾，但混在一起讲就会让人以为 git 变更也是秒级的。

## 八、把这条链路自己验一遍

不需要读代码就能确认这条链路是活的，按顺序敲：

```bash
# 内循环：改一行、看到变化，全程不碰 git
#   main.go 里 handleGreet 的默认 name 从 "world" 改成 "cnlab"
make image-push-local
kubectl --context kind-cnlab -n cnlab-dev rollout restart deploy/cnlab
kubectl --context kind-cnlab -n cnlab-dev rollout status  deploy/cnlab
make smoke                       # /api/v1/greet 应该回 cnlab, cnlab!

# 外循环：push 之后什么都不用做
git add -A && git commit -m "test inner loop" && git push origin main
gh run watch                     # 看四个 job 依次变绿
make argo-status                 # cnlab-staging 应变成 OutOfSync → Synced

# 确认没有人在集群里敲过 apply
kubectl --context kind-cnlab -n cnlab-staging get deploy cnlab \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
# 期望：ghcr.io/am-okalin/cnlab:sha-<这次 push 的 7 位 sha>

kubectl --context kind-cnlab -n cnlab-staging port-forward svc/cnlab 8081:80 &
curl -s http://127.0.0.1:8081/api/v1/version; echo
# 期望：version 与上面 image 的 tag 完全一致，commit 是完整 sha
```

最后那两条命令是整条链路的**自证**：镜像地址来自 git 里被 CI 写回的期望状态，而运行中的进程又用自己的 `/api/v1/version` 报告它到底是哪个 commit。两边对得上，才说明"线上跑的是哪份代码"这个问题真的能被回答。

实测闭环记录：CI 把 `sha-f24b9a4` 写回 `deploy/overlays/staging` 并提交，ArgoCD 同步后 staging 运行 `ghcr.io/am-okalin/cnlab:sha-f24b9a4`，`/api/v1/version` 自报 `version=sha-f24b9a4`、`commit=f24b9a4e80edcb80af918e8ca06524333ae11ccf`。

注意这两个字段的**粒度不同**：`version` 是 CI 计算的短 sha（`sha-${GITHUB_SHA::7}`），而 `commit` 来自构建参数 `COMMIT=${{ github.sha }}`，是完整 40 位 sha。它们指向同一个提交，只是截断长度不同。

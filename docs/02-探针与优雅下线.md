# 探针与优雅下线

这是整个项目最核心的一篇。滚动更新能做到零中断，靠的不是某一个 YAML 字段，而是**三种探针 + 应用内的一段退出逻辑 + 一个时间预算**三者严丝合缝地配合。

只要其中任何一环理解错了，故障现象都会长得很像：偶发 502、更新卡住、Pod 被无谓重启。

## 一、三种探针，三种完全不同的后果

| 探针 | 回答的问题 | 失败后 kubelet 做什么 | 失败代价 |
|---|---|---|---|
| `startupProbe` | 启动完成了没？ | 继续等；超过 `failureThreshold × periodSeconds` 才杀容器 | 启动慢的服务被误杀 |
| `livenessProbe` | 进程还活着吗？ | **重启容器** | 依赖抖动被放大成连环重启 |
| `readinessProbe` | 现在能导流量吗？ | 从 Service endpoints **摘除**，不重启 | 通常无害，本该如此 |

三者的边界，可以用一句话记：**liveness 决定"要不要重启你"，readiness 决定"要不要给你流量"，startup 决定"前面两个先别管"。**

### 为什么 liveness 绝不能检查下游依赖

这是最常见、后果最严重的一个误用。

假设你把 liveness 做成"能连上数据库才算活着"。某天数据库出现 200ms 抖动：

```
数据库抖动
  → 所有 Pod 的 liveness 同时失败
  → kubelet 同时重启所有 Pod
  → 数据库瞬间失去所有连接池，压力反而更大
  → 抖动变成宕机
```

一次本来 200ms 就能自愈的小故障，被放大成一次雪崩。**liveness 只应该回答"这个进程本身是否还值得存在"**：死锁、goroutine 泄漏到无法服务、事件循环卡死——这些才是该重启的信号。

所以本项目的 `/healthz` 什么都不检查：

```go
func handleHealthz(w http.ResponseWriter, _ *http.Request) {
	writeJSON(w, http.StatusOK, map[string]any{
		"status": "ok",
		"uptime": time.Since(startTime).Round(time.Millisecond).String(),
	})
}
```

### 为什么 startupProbe 必须打对端点

如果没有 startupProbe，你只有两个选择，都很糟：

- 把 liveness 的 `initialDelaySeconds` 调大 —— 等于同时放宽了对"运行中卡死"的检测，卡死也要等那么久才被发现；
- 不管 —— 启动慢的服务会被 liveness 反复杀掉，表现为 `CrashLoopBackOff`，而日志里一切正常。

startupProbe 的价值就是**把"启动慢"和"运行中卡死"这两个问题解耦**。在它成功之前，liveness 和 readiness 都不会执行——启动期因此拿到了自己独立的一份预算。

**但这里有个前提：startupProbe 必须打一个"启动没完成时确实会失败"的端点。**

本项目在写这份文档时踩了这个坑：`startupProbe` 一开始打的是 `/healthz`，而 `/healthz` 从进程开始监听的第一刻就返回 200。结果 `failureThreshold: 30` 一次都用不上——探针第一次探测就通过，启动期根本没被"看住"。这类错误**不会报错**，清单渲染正常、Pod 正常启动，只有做对照实验才能发现。

正确做法是打 `/readyz`。下面是在本机跑出来的对照实验（`READY_DELAY=45s`，且为了制造问题，把 liveness 也指向 `/readyz`）：

| 变体 | startupProbe | 观察结果 |
|---|---|---|
| A | 无 | 每 ~30s 被杀一次（`periodSeconds 10 × failureThreshold 3`），RESTARTS 持续增长到 3，**永远到不了 Ready** |
| B | 有，打 `/readyz` | **RESTARTS 恒为 0**，45 秒预热完成后正常就绪 |

差别全部来自"startupProbe 期间 liveness 被挂起"。没有它，liveness 在预热还没结束时就按自己的阈值开始判死刑，而容器每次被杀都会让预热计时从头开始 —— 于是陷入永远起不来的循环。这正是生产上 `CrashLoopBackOff` 最常见的成因之一，而根因（探针打错端点）通常被误诊成"应用启动有问题"。

想自己复现这套对照，见[动手练习 1.1](07-动手练习.md)；本项目的 `startupProbe` 配置见 [deploy/base/deployment.yaml](../deploy/base/deployment.yaml)。

顺带记住一个容易踩的顺序问题：**单独把 `READY_DELAY` 调大并不会导致重启**。因为 `/healthz` 与它无关，Pod 只会停在 `0/1`（不导流量）。要看到重启，必须让 liveness 依赖预热状态——而那本身就是需要避免的误用。这个"看起来该出问题却没出"的现象，恰恰是判断探针有没有配对的最好线索。

## 二、SIGTERM 之后到底应该发生什么

Pod 被删除时，Kubernetes 会**并发**做两件事：

1. 控制面把 Pod 从 Service 的 endpoints 里摘除；
2. kubelet 向容器的 PID 1 发送 SIGTERM。

**第 1 件事不是瞬时的。** endpoints 变更要经过 kube-proxy 同步到每个节点上的 iptables/ipvs 规则，这需要时间。在这个窗口里，Service 的转发规则可能还指着这个 Pod。

于是就有了那个经典的错误做法：收到 SIGTERM 立刻退出。后果是：

```
t=0    SIGTERM 到达，进程立刻 os.Exit(0)
t=0    endpoints 摘除还在传播中
t=0~?  新连接仍被 kube-proxy 转发到这个已经死掉的 Pod
       → connection refused → 客户端看到 502
```

正确做法是把退出拆成三步，顺序不能换。本项目 `main.go` 的 `run()` 里就是这么写的：

```
t=0       收到 SIGTERM（signal.NotifyContext 取消 ctx）
          │
t=0       第 1 步：ready.Store(false)
          │   /readyz 立即开始返回 503
          │   进程仍在正常服务，只是不再适合接收"新"流量
          │
t=0~D     第 2 步：等待 DRAIN_DELAY（本 base 默认 5s）
          │   这段时间用来让"摘除"动作在集群内传播完成
          │   同时继续把已经打进来的请求处理完
          │
t=D       第 3 步：srv.Shutdown(ctx)
          │   关闭监听器（不再接受新连接）
          │   阻塞等待在途请求返回，直到成功或 SHUTDOWN_TIMEOUT 到期
          │
t=D+ε     所有请求结束 → 进程退出，exit 0
```

对应代码：

```go
a.ready.Store(false)                       // 第 1 步：先摘流量
// ...
select {
case <-drain.C:                            // 第 2 步：等传播
case <-time.After(c.ShutdownTimeout):
}
// ...
if err := srv.Shutdown(shutdownCtx); err != nil {   // 第 3 步：等待在途请求
```

### DRAIN_DELAY 存在的唯一理由

它**不是**用来"等在途请求结束"的 —— 那是 `srv.Shutdown` 的职责。它唯一的用途是等待 endpoints 摘除在集群内传播完成。

理解这一点之后，两个结论就自然了：

- **`DRAIN_DELAY = 0` 会在滚动更新时产生 502。** 因为摘除还没生效，新连接还在往这个 Pod 上打，而监听器已经关了。
- **`DRAIN_DELAY` 的大小和"流量规模"相关，而不是和"请求耗时"相关。** 集群越大、节点越多，endpoints 传播越慢。

亲手验证：

```bash
# 把 dev 的 DRAIN_DELAY 改成 0，再跑零中断压测
kubectl -n cnlab-dev set env deploy/cnlab DRAIN_DELAY=0s
make zero-downtime          # 观察 fail 计数是否不再为 0

# 改回来
kubectl -n cnlab-dev set env deploy/cnlab DRAIN_DELAY=3s
```

### 为什么本项目不用 preStop sleep

网上流传最广的写法是加一个钩子：

```yaml
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 5"]
```

它确实能"work around"这个问题，但本项目刻意不用，有两个理由：

1. **它在容器里浪费 5 秒**，而且这 5 秒和 `terminationGracePeriodSeconds` 是双重计时的，预算很容易算错。distroless 镜像里更是连 `/bin/sh` 都没有，这个钩子根本写不出来。
2. **更根本的是位置错了。** `preStop sleep` 的潜台词是"我的应用不会优雅退出，所以在外面糊一层"。而这个逻辑本来就该由应用自己表达——它更精确（应用自己知道什么时候该停止接收流量）、可观测（有日志）、可测试（本项目的 `TestGracefulShutdownDrainsInFlight` 就是直接断言它）。

这是本项目贯穿始终的一个取向：**优先把行为做进应用，而不是用外部手段补偿应用的行为。**

## 三、时间预算必须对齐

三个时间参数必须满足：

```
terminationGracePeriodSeconds  ≥  DRAIN_DELAY + 最长请求耗时 + 余量
```

| 参数 | 谁在用 | 作用 |
|---|---|---|
| `DRAIN_DELAY` | 应用（环境变量） | SIGTERM 后、关闭监听器前的等待 |
| `SHUTDOWN_TIMEOUT` | 应用（环境变量） | `srv.Shutdown` 等待在途请求的上限 |
| `terminationGracePeriodSeconds` | kubelet（Pod spec） | 从发 SIGTERM 到强杀 SIGKILL 的总预算 |

各环境的实际取值：

| 环境 | DRAIN_DELAY | SHUTDOWN_TIMEOUT | terminationGracePeriodSeconds |
|---|---|---|---|
| dev | 3s | 10s | 30s（base） |
| staging | 5s | 15s | 30s（base） |
| prod | 10s | 20s | 45s |

**对不齐的后果非常具体**：`terminationGracePeriodSeconds` 小于 `DRAIN_DELAY` 时，kubelet 会在应用还在 drain 的时候就 SIGKILL 它。现象是日志里**看不到**「已优雅退出」那一行——进程没有机会走到那里。同时会偶发 502。

亲手验证：

```bash
kubectl -n cnlab-dev patch deploy cnlab --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/terminationGracePeriodSeconds","value":1}]'
kubectl -n cnlab-dev rollout restart deploy cnlab
kubectl -n cnlab-dev logs -l app.kubernetes.io/name=cnlab --previous | tail
# 只能看到「等待流量摘除」，看不到「已优雅退出」
```

## 四、一个真实的坑：StateNew 连接让 Shutdown 卡满 5 秒

这个是本项目**实际踩到并修掉**的，值得单独讲，因为它同时影响测试和生产。

### 现象

`TestGracefulShutdownDrainsInFlight` 这个测试**偶发失败**：同一个测试，有时 0.85 秒通过，有时 5.2 秒超时。日志显示：

```
msg=已优雅退出 grace=4.744s      ← 注意这个 grace
```

`grace` 是从调用 `srv.Shutdown` 到它返回的耗时。drain 只配了 800ms，Shutdown 却花了 4.744 秒，且这个数字每次都不同但总是接近 5 秒。

### 根因

`net/http` 的 `Server.Shutdown` 在关闭连接时，对处于 **StateNew** 状态（TCP 已 accept，但还没读到任何请求字节）的连接有特殊处理：

```go
// net/http/server.go, closeIdleConns()
// Issue 22682: treat StateNew connections as if they're idle if we haven't
// read the first request's header in over 5 seconds.
if st == StateNew && unixSec < time.Now().Unix()-5 {
    st = StateIdle
}
```

也就是说，一个"连上了但没发请求"的连接，要等它闲置满 **5 秒**才肯被关闭，`Shutdown` 就只能干等。

而 HTTP 连接池复用非常容易制造这种连接：客户端复用了连接、或者连接刚建立还没来得及发请求，服务端那边就是一个 StateNew 连接。

### 在测试里怎么修的

测试客户端关掉 keep-alive，让每个请求一条连接、用完即关：

```go
var testClient = &http.Client{
	Transport: &http.Transport{DisableKeepAlives: true},
	Timeout:   10 * time.Second,
}
```

并且加了一条回归护栏，防止以后有人改回去：

```go
// 退出总耗时应该约为 DRAIN_DELAY，而不是被 StateNew 连接的 5s 兜底拖住。
if elapsed := time.Since(start); elapsed > 3*time.Second {
	t.Errorf("优雅退出耗时 %v，远超 DRAIN_DELAY（预期约 0.8s）", elapsed.Round(time.Millisecond))
}
```

修完之后连跑 5 次（带 `-race` 和不带）全部通过，5 次总耗时从 27 秒降到 6.3 秒。

### 对生产的影响

这个坑在生产里**同样存在，而且无法靠改客户端回避**：

> **kubelet 的探针每次都会新建 TCP 连接。**

如果探针的连接恰好落在"已 accept 但还没发请求"的状态，`Shutdown` 就可能被拖住最多 5 秒。

结论是一条很实用的经验：**`terminationGracePeriodSeconds` 不能按"DRAIN_DELAY + 请求耗时"贴着算，必须留出至少 5 秒以上的余量。** 本项目各环境都留了足够余量（dev：3+10 对 30s；prod：10+20 对 45s）。

## 五、实测证据

### 容器层面（`docker stop`）

```
在途请求: GET /api/v1/slow?d=600ms  → 200，耗时 0.604s
docker stop 耗时: 0.94s             （DRAIN_DELAY=800ms）

容器日志：
  msg="HTTP 服务启动" addr=[::]:8080 pid=1
  msg=已就绪，开始接收流量
  msg=收到终止信号，开始优雅下线
  msg=就绪探针已置为失败，等待流量摘除 drain_delay=800ms
  msg=已优雅退出 grace=0s
```

注意 `pid=1`：distroless + exec 形式的 ENTRYPOINT，让应用直接成为 PID 1，SIGTERM 直达，中间没有 shell 吞信号。这也是 `docker stop` 只用 0.94s 而不是等满 10 秒默认超时的原因。

### Kubernetes 层面（滚动更新）

`make zero-downtime` 会在集群内启动压测 Pod 走 Service 访问，然后在压测进行中触发滚动更新：

```
压测结果：            RESULT total=60 ok=60 fail=0
被替换 Pod 的日志：
  已就绪，开始接收流量
  收到终止信号，开始优雅下线
  就绪探针已置为失败，等待流量摘除 drain_delay=3s
  已优雅退出 grace=0s
```

**60 个请求零失败**，且旧 Pod 走完了全部三步。

压测刻意走集群内的 Service 而不是本机 `kubectl port-forward`，原因见 [踩坑记录](06-踩坑记录.md) 里的"用 port-forward 测零中断"一条——那是一种会自己制造失败的测法。

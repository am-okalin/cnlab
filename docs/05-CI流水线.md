# 05 · CI 流水线：四个 job 各在防什么

`.github/workflows/ci.yml` 一共 264 行，四个 job。这篇文档逐个拆开，重点不在"它做了什么"，而在"它为什么这么做"以及"少了这一步会出什么事"。

---

## 一、先看最反常的地方：这里没有 deploy

打开工作流，第一个注释块就先声明了这件事：

```yaml
# 这个工作流里没有 "deploy" 这一步，这是刻意的。
#
# 在 GitOps 模型下，CI 的职责到"把镜像推进仓库、把新 tag 写回期望状态"就结束了。
# 真正让集群发生变化的，是集群里的 ArgoCD 发现 git 变了。
```

所以最后一个 job 叫 `gitops` 而不是 `deploy`。它做的是**提交一个新的期望状态**：

```bash
kustomize edit set image "cnlab=ghcr.io/am-okalin/cnlab:sha-f24b9a4"
git commit -m "chore(gitops): staging -> sha-f24b9a4 [skip ci]"
git push origin main
echo "已提交。接下来由集群内的 ArgoCD 发现变化并同步。"
```

整条流水线里没有任何 `kubectl`。这个选择的完整理由（凭证边界）在 [GitOps 与 ArgoCD](04-GitOps与ArgoCD.md) 里展开，这里只需要记住一条推论：

**"没有 deploy job"不是漏了，而是这条流水线的设计目标之一。** 一旦在这里加 `kubectl apply`，集群凭证就必须搬进 CI secret，ArgoCD 的持续漂移检测也就失去意义了。

### 四个 job 的依赖关系

```yaml
jobs:
  quality:    # 无 needs → 立即开始
  manifests:  # 无 needs → 立即开始（与 quality 并行）
  image:      # needs: quality
  gitops:     # needs: image, 且 if: github.ref == 'refs/heads/main'
```

画成图：

```
        ┌──────────┐
        │ quality  │──────────┐
        └──────────┘          ▼
                        ┌──────────┐     ┌──────────┐
        ┌──────────┐    │  image   │────▶│  gitops  │
        │manifests │    └──────────┘     └──────────┘
        └──────────┘      (needs quality)  (main 分支才跑)
                        └── 只有 image 等 quality；manifests 独立
```

第二次运行（全绿）的耗时：

| job | 耗时 |
|---|---|
| 质量门 | 18s |
| 校验清单 | 24s |
| 构建镜像 | 51s |
| 更新 staging 期望状态 | 12s |

`image` 是最长的一环，它决定整条流水线的墙钟时间。

## 二、`quality`：为什么工具版本必须锁死

```yaml
quality:
  name: 质量门
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v7

    - uses: actions/setup-go@v7
      with:
        go-version-file: go.mod      # ← 版本来自 go.mod
        cache: true

    - name: 检查格式
      run: |
        unformatted=$(gofmt -l $(git ls-files '*.go'))
        if [ -n "$unformatted" ]; then
          echo "以下文件未格式化，请本地执行 make fmt："
          echo "$unformatted"
          exit 1
        fi

    - name: go vet
      run: go vet ./...

    - name: golangci-lint
      uses: golangci/golangci-lint-action@v9
      with:
        version: v2.12.2             # ← 写死的版本

    - name: 测试（含竞态检测）
      run: go test -race -count=1 -coverprofile=coverage.out ./...

    - name: 覆盖率
      run: go tool cover -func=coverage.out | tail -1
```

### Go 版本：`go-version-file: go.mod`

不写 `go-version: '1.25'`，而是让 setup-go 去读 `go.mod`（本项目是 `go 1.25.12`）。这样**只有一处**定义 Go 版本。如果 CI 写一个、`go.mod` 写另一个，两者开始漂移时没有任何机制会提醒你，直到某次 CI 挂在一个本地复现不出来的问题上。

### golangci-lint 版本：`v2.12.2`

注释说得直接：

```yaml
# 用和本地完全相同的 golangci-lint 版本。
# 版本不一致会导致"本地过、CI 挂"或反过来，是最消耗耐心的那类问题。
```

本机 `golangci-lint --version` 是 `2.12.2`，和这里是同一个值。lint 工具的版本漂移比 Go 版本漂移更阴险，因为**规则集**会随版本变化：某个版本新启用了一条 linter，CI 立刻开始报一堆本地看不到的错，而这些错通常和当次改动毫无关系。

这类问题的成本不在于修，而在于**定位**：开发者看到 CI 红了，第一反应是怀疑自己刚写的代码，于是去逐个排查 20 个与本次改动无关的告警。把版本锁死，是把这个成本降到零的最便宜手段。

顺带注意：本地 `make lint` 和 CI 走的是**同一个版本号**，但**不是同一个二进制**（本地是 goenv 软链的，CI 是官方 action 提供的）。版本一致就够了，来源不一致不影响结果。

### 格式检查为什么是 `git ls-files '*.go'` 而不是 `gofmt -l .`

这一行看起来啰嗦，但它躲开一个本机特有的坑。本项目的 Go 缓存被放在项目内的 `.cache/` 下（见 `hack/env.sh`），而 `gofmt` 是**自己遍历文件系统**的工具（它不像 `go vet ./...` 那样由 go 工具链驱动，后者会跳过以 `.` 开头的目录）。结果：

- `gofmt -l .` 会递归进 `.cache/gomodcache`，检查成千上万个第三方库和 Go 工具链自身的源文件；
- 既慢得离谱，又会刷出一屏"未格式化"的**误报**——工具链的测试数据里本来就有故意不合法的 Go 源码。

`make fmt-check` 用的是同一个表达式（`GOSOURCES := $(shell git ls-files '*.go')`），所以本地和 CI 的判断标准完全一致。这也是一个更普遍的原则：**CI 里的检查命令应该和本地是同一句话**，否则你会拥有两套结论。

### `-race` 不是凑数

```bash
go test -race -count=1 -coverprofile=coverage.out ./...
```

本项目只有一个源文件，但 `main_test.go` 会驱动真实的服务生命周期（含优雅退出），里面同时跑着 HTTP 服务、信号处理和在途请求的收尾。这是竞态检测真正有价值的地方——**优雅退出这类逻辑的 bug 只在并发下出现**，而它们在线上的表现是间歇性 502，几乎不可能靠读代码发现。

`-count=1` 关掉测试结果缓存，保证每次都真的跑。

## 三、`manifests`：`kustomize build` 不够，还要 schema 校验

```yaml
manifests:
  name: 校验清单
  steps:
    - uses: actions/checkout@v7
    - uses: actions/setup-go@v7
      with:
        go-version-file: go.mod

    - name: 安装 kustomize（与本地同一版本）
      run: ./hack/install-tools.sh

    - name: 渲染全部 overlay
      run: |
        for dir in deploy/overlays/*/; do
          kustomize build "$dir" > "/tmp/manifests/${name}.yaml"
        done

    - name: 校验 Kubernetes schema
      run: |
        curl -sSL -o /tmp/kubeconform.tar.gz \
          "https://github.com/yannh/kubeconform/releases/download/v0.8.0/kubeconform-linux-amd64.tar.gz"
        tar -xzf /tmp/kubeconform.tar.gz -C /tmp kubeconform
        for f in /tmp/manifests/*.yaml; do
          /tmp/kubeconform -strict -summary -ignore-missing-schemas "$f"
        done
```

### 为什么需要第二层

```yaml
# kustomize build 只保证"能渲染"，不保证"字段合法"。
# kubeconform 拿官方 JSON Schema 做离线校验，能在合并前抓出
# 拼错的字段名、放错层级的字段、以及引用了不存在的 apiVersion。
```

这两件事的差别值得用一个具体例子说明。在 [Kustomize 多环境](03-Kustomize多环境.md) 里我试过一个拼错 container 名字的 patch：`kustomize build` **退出码 0**，静默渲染出一个多了一个容器的 Deployment。这就是"能渲染"和"合法"之间的距离。

`kustomize build` 的职责是**合并逻辑**（base + overlay + patch 拼起来对不对），它不读 Kubernetes 的 schema，所以没有能力判断字段对不对。两层检查回答的是两个不同的问题：

| 层 | 命令 | 回答的问题 |
|---|---|---|
| 渲染 | `kustomize build` | 合并逻辑成立吗？ |
| Schema | `kubeconform -strict` | 字段名、层级、apiVersion 合法吗？ |

实测三个 overlay 的结果：

```console
--- dev
Summary: 5 resources found in 1 file - Valid: 5, Invalid: 0, Errors: 0, Skipped: 0
--- staging
Summary: 5 resources found in 1 file - Valid: 5, Invalid: 0, Errors: 0, Skipped: 0
--- prod
Summary: 6 resources found in 1 file - Valid: 6, Invalid: 0, Errors: 0, Skipped: 0
```

两个参数的作用：`-strict` 会把未知字段当错误（默认只是警告），这样才能抓住拼错的字段名；`-ignore-missing-schemas` 避免因为某个 CRD 没有公开 schema 就整体失败。

### 这里有一个真实的失败

第一次运行时这个 job 挂了，报错是：

```console
go: github.com/yannh/kubeconform/cmd/kubeconform@v0.8.0: 
    requires go >= 1.26 (running go 1.25.12; GOTOOLCHAIN=local)
##[error]Process completed with exit code 1.
```

当时的写法是 `go install github.com/yannh/kubeconform/cmd/kubeconform@v0.8.0`。根因是两个设置撞在一起：

1. kubeconform v0.8.0 要求 `go >= 1.26`；
2. `actions/setup-go` 默认会设 `GOTOOLCHAIN=local`，禁止 Go 自动下载更新的工具链，而按 `go.mod` 装的是 1.25.12。

于是 `go install` 没有走"自动切换到 1.26 工具链"这条路，直接失败。现在的写法是下载官方预编译二进制，顺带省掉编译时间：

```yaml
# 这里刻意用官方预编译二进制，而不是 `go install`：
# kubeconform v0.8.0 要求 go >= 1.26，而 actions/setup-go 默认会设
# GOTOOLCHAIN=local，禁止自动下载更新的工具链……
# 用发布二进制还顺带省掉了编译时间。
```

对照 `quality` job：`golangci-lint` 用的是官方 action，同样没有走 `go install`。**在 CI 里装工具，"下载预编译二进制"通常比"用 go install 编译"更稳**——它把 Go 工具链版本的耦合去掉了。

### `manifests` 失败其实拦不住后面

这是一个值得注意的结构事实。`manifests` job **没有 `needs:`**，而 `image` 只 `needs: quality`，`gitops` 只 `needs: image`。所以 `manifests` 失败**不会**阻止镜像构建和 GitOps 写入。

这不是推测，第一次运行就是这个样子：

| job | 结果 | 时间 |
|---|---|---|
| 质量门 | 成功 | 05:30:02 → 05:30:42 |
| 校验清单 | **失败**（kubeconform 装不上） | 05:30:03 → 05:30:15 |
| 构建镜像 | 成功 | 05:30:47 → 05:31:54 |
| 更新 staging 期望状态 | 成功，写入 `latest` | 05:31:59 → 05:32:09 |

校验清单在 05:30:15 就失败了，而镜像照样构建推送，`gitops` 照样把新 tag 提交进了仓库（就是那次产生 `chore(gitops): staging -> latest` 的运行）。

但 job 自己的注释写的是：

```yaml
# 2. 清单校验：清单改坏了必须在这里被拦住
```

**注释表达的意图（拦住）和结构表达的行为（拦不住）不一致。** 如果确实希望"清单改坏了就不许发布镜像、不许更新期望状态"，需要把 `manifests` 接进依赖链：

```yaml
image:
  needs: [quality, manifests]     # ← 这样才真正构成门禁
```

代价是失去并行：`manifests` 的 24s 会加到 `image` 之前，总时长变长。是否值得取决于你怎么看"一个渲染不出合法清单的提交要不要发布镜像"。对一个以教学为目的的项目，两种选择都能自圆其说；但**留一句与行为不符的注释**是应该避免的——它会让下一个读代码的人以为自己受到了一道不存在的保护。

## 四、`image`：多架构构建，以及为什么没有 QEMU

```yaml
image:
  needs: quality
  permissions:
    contents: read
    packages: write
  outputs:
    tag: ${{ steps.tag.outputs.value }}
    digest: ${{ steps.build.outputs.digest }}
```

### 没有 `setup-qemu-action` 是刻意的

这是这份流水线里最容易被"纠正"成错误的一处。绝大多数多架构构建的示例都会在 `setup-buildx-action` 后面跟一个 `setup-qemu-action`，而这里没有：

```yaml
# 这里刻意没有 setup-qemu-action。
# 因为 Dockerfile 的构建阶段用了 --platform=$BUILDPLATFORM，
# 交叉编译由 Go 自己完成（GOARCH），并不需要真的执行目标架构的二进制。
# 少装 QEMU，构建快一个数量级。
```

机制在两处配合：

```dockerfile
# Dockerfile
FROM --platform=$BUILDPLATFORM golang:1.25-alpine AS builder   # ← 构建阶段跑在原生架构
ARG TARGETOS
ARG TARGETARCH
RUN CGO_ENABLED=0 GOOS=${TARGETOS:-linux} GOARCH=${TARGETARCH} \
    go build ... -o /out/cnlab .
```

- `--platform=$BUILDPLATFORM` 让**构建阶段本身**运行在 runner 的原生架构上（amd64 runner 上就跑 amd64 的 golang 镜像）。
- `TARGETOS` / `TARGETARCH` 由 buildx 自动注入，Go 用 `GOOS` / `GOARCH` 自己产出目标架构的二进制。

所以整个构建过程中**没有任何一步需要执行目标架构的程序**。QEMU 的作用是模拟执行，没有东西要执行，它就白装了——而"白装"的代价是构建阶段会变成模拟执行，慢一个数量级。

**什么情况下必须把 QEMU 加回来**：构建阶段需要**运行**目标架构的东西。例如：

- 在构建阶段 `apt install` 某个 arm64 的包；
- `RUN` 一个目标是 arm64 的二进制（代码生成器、编译器插件）；
- 构建链路里有一环不是 Go，或者依赖 cgo 交叉编译工具链。

判据是一句话：**构建阶段有没有"执行"目标架构的程序**。只有"产出"目标架构的产物，就不需要 QEMU。

### 登录只在 push 时发生

```yaml
- name: 登录 GHCR
  if: github.event_name == 'push'
  uses: docker/login-action@v4
  with:
    registry: ${{ env.REGISTRY }}
    username: ${{ github.actor }}
    password: ${{ secrets.GITHUB_TOKEN }}
```

`GITHUB_TOKEN` 是每个工作流自动注入的短期凭证，**不需要自己配 secret**。PR 不登录，因为 PR 不推送。

### 显式计算 tag，不依赖 action 的输出

```yaml
- name: 计算不可变 tag
  id: tag
  run: |
    set -euo pipefail
    if [[ "${GITHUB_REF_TYPE}" == "tag" ]]; then
      echo "value=${GITHUB_REF_NAME}" >> "$GITHUB_OUTPUT"     # 打 tag 时用 tag 名
    else
      echo "value=sha-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"   # 否则用短 sha
    fi
```

代码旁边的注释记录了为什么不用 `metadata-action` 的 `version` 输出：

```yaml
# 这是一个真实踩到的坑：metadata-action 的 version 输出会按优先级挑一个
# tag，而 type=raw,value=latest 的优先级高于 type=sha，于是拿到的是
# "latest"。用它去更新期望状态，等于把不可追溯的 latest 写进了 GitOps
# 仓库 —— 正好破坏掉"用不可变 tag 才能回答线上跑的是哪份代码"这个前提。
# 自己算最直白，也不用去记 action 的优先级规则。
```

这件事故的完整经过（包括它如何让回滚变得不可能）写在 [GitOps 与 ArgoCD](04-GitOps与ArgoCD.md) 里。这里只提炼一句：**第三方 action 的输出，如果会被下游依赖，就值得显式算一遍或断言一次。** 那次失败不是因为 action 出错，而是因为没人检查它输出的到底是什么。这个 tag 后来一路传到 staging 的 ConfigMap、Pod 镜像和 `/api/v1/version` 的自报字段，是所有追溯性的起点。

`metadata-action` 仍然保留，但只用来生成 tags 和 OCI labels：

```yaml
- name: 生成镜像标签与 OCI 元数据
  id: meta
  uses: docker/metadata-action@v6
  with:
    images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
    tags: |
      type=raw,value=${{ steps.tag.outputs.value }}   # 主 tag：上面算出的不可变值
      type=raw,value=latest,enable={{is_default_branch}}   # 方便人类，生产别用
```

### 构建并推送

```yaml
- name: 构建并推送（amd64 + arm64）
  uses: docker/build-push-action@v7
  with:
    context: .
    platforms: linux/amd64,linux/arm64
    # PR 只构建不推送：PR 来自 fork 时本来也拿不到 packages:write，
    # 而且"合并才发布"是应有的纪律。
    push: ${{ github.event_name == 'push' }}
    build-args: |
      VERSION=${{ steps.tag.outputs.value }}
      COMMIT=${{ github.sha }}
      BUILD_TIME=${{ steps.buildmeta.outputs.time }}
    cache-from: type=gha
    cache-to: type=gha,mode=max
```

`push: ${{ github.event_name == 'push' }}` 让 PR 只构建、不推送，理由有三层：

1. **权限上本来就做不到**——fork PR 拿不到 `packages: write`；
2. **纪律上"合并才发布"**——PR 期间不应该产生任何可被部署的产物；
3. **价值上仍然值得跑**——PR 阶段就能验证多架构构建真的能过。如果只在 push 后才构建，架构相关的问题要等合并了才暴露，而那时它已经在 main 上了。

`cache-from/to: type=gha` 用 GitHub Actions 的缓存后端跨运行复用构建层。对多架构构建这一项尤其重要——两条架构的构建层都靠它。

三个 build-args 最终变成运行时可见的东西：

```console
$ curl -s http://127.0.0.1:18080/api/v1/version
{"version":"sha-f24b9a4","commit":"f24b9a4e80edcb80af918e8ca06524333ae11ccf", ...}
```

`VERSION` 是 tag（短 sha），`COMMIT` 是 `github.sha`（完整 40 位）。两个粒度不同但指向同一个提交——这是"镜像 tag ↔ git commit ↔ 运行时自报"三方一致链条的最后一环。

## 五、`gitops`：交接点，以及它为什么不会死循环

```yaml
gitops:
  name: 更新 staging 期望状态
  needs: image
  # 只有合并进 main 才更新期望状态。tag 构建用于发布，
  # 不走这条自动路径 —— 生产要人工提升。
  if: github.ref == 'refs/heads/main'
  permissions:
    contents: write
```

### 它只改一个字段

```yaml
- name: 把新镜像写进 staging overlay
  run: |
    export PATH="$PWD/bin:$PATH"
    cd deploy/overlays/staging
    kustomize edit set image "cnlab=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ needs.image.outputs.tag }}"
```

`kustomize edit set image` 改的就是 `deploy/overlays/staging/kustomization.yaml` 的 `images` 段。**CI 不需要理解 Deployment 长什么样**——它只需要会改这一个字段，然后把渲染交给 ArgoCD 的 repo-server。这个狭窄的接口就是 CI 和 CD 之间的契约。

（注意这里也先跑 `./hack/install-tools.sh`，用和 `manifests` job、和本地**同一个** kustomize v5.8.3。版本不一致的话，CI 写出来的格式可能和本地 `kustomize edit` 的产物不一样，产生莫名其妙的 diff。）

### 幂等：没变化就不提交

```yaml
git add deploy/overlays/staging/kustomization.yaml

# 幂等：镜像 tag 没变就什么都不做，避免制造无意义的空提交。
if git diff --cached --quiet; then
  echo "期望状态无变化，跳过提交"
  exit 0
fi
```

没有这一段，重复运行会产生一串内容相同的 commit，把 git 历史淹掉。

### 为什么不会无限循环

`gitops` job 推送了一次 commit，而这个 commit 又落在 `main` 上。如果不做处理，这次 push 会触发新的 workflow run，新的 run 又跑一次 `gitops`，又 push 一次……这里有两道**互相独立**的防线。

**第一道：commit message 里的 `[skip ci]`**

```bash
git commit -m "chore(gitops): staging -> ${{ needs.image.outputs.tag }} [skip ci]"
```

**第二道：用 `GITHUB_TOKEN` 推送的提交本身不会触发工作流。**

这是更重要的一道，也是更根本的一道。GitHub 的防递归机制规定：用仓库自己的 `GITHUB_TOKEN` 执行操作所触发的事件，不会创建新的 workflow run。而 `actions/checkout` 默认就用 `github.token` 配置推送凭证，所以 `git push origin main` 走的正是 `GITHUB_TOKEN`。

**为什么两道都要有**，而不是留一道就够：

| 防线 | 在什么时候失效 |
|---|---|
| `[skip ci]` | 只在 GitHub Actions 上有效。换到别的 CI，或者换一个不认这个标记的系统，它就没了 |
| `GITHUB_TOKEN` 机制 | 一旦有人把凭证换成 PAT 或 Deploy Key（为了触发下游工作流、或者推送受保护分支），这道防线立刻失效 |

现实中"用 PAT 推送"是很常见的调整（想让这次提交触发别的流水线）。那一刻，`GITHUB_TOKEN` 的保护就没了，**只剩下 `[skip ci]`**。所以两道都留着是合理的纵深防御，而不是冗余。

还有第三道弱一点的保险：上面那段幂等检查。即使前两道都失效，第二次运行的 tag 没变化 → 不提交 → 循环也会停。但它只在"重复运行产生相同结果"时有效，不能当成主要防线。

### tag 构建不走这条路

```yaml
if: github.ref == 'refs/heads/main'
```

打 `v*` tag 时只构建镜像、不更新期望状态。所以发布和部署是两件事：打 tag 产出可发布产物，**生产环境的提升由人来做**。这和 `gitops/examples/cnlab-prod.yaml` 不给 `automated` 是同一个思路的两端。

## 六、`concurrency`：在防一个很具体的竞态

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

注释写的是：

```yaml
# 同一个分支只保留最新一次运行：
# 既省配额，也避免"旧提交的镜像后推上去、覆盖新提交"的竞态。
```

这个竞态值得展开，因为它**不是理论上的**。连续两次快 push（`commit A` 然后 `commit B`）时：

```
时间线（没有 concurrency 时）：
  run(A): 开始 ──────────────▶ 推镜像 sha-A ──▶ gitops 写 sha-A
  run(B):      开始 ──────────────▶ 推镜像 sha-B ──▶ gitops 写 sha-B
                                    ↑
                        B 先完成，写 sha-B
                        
  然后 A 的 gitops 才跑完 → 把 sha-A 写回去
  结果：期望状态回退到旧提交
```

最终集群里跑的是 **A 的代码**，而 git 的最新提交是 B 的期望状态被 A 覆盖后的样子。表现为"我刚推的改动没有生效，而且 git 里显示的也是对的"——非常难排查。

`cancel-in-progress: true` 让同一分支只保留最新一次运行，旧运行被直接取消。

**代价**要注意两点：

1. 正在跑的长任务会被取消，如果某个 job 有副作用（比如已经推了镜像），取消不会回滚它。本项目能接受，因为镜像只是多了一个不被引用的 tag。
2. `group` 里带了 `${{ github.ref }}`，所以 **tag 构建和 main 分支构建互不干扰**——`v1.0.0` 的发布不会因为 main 有新提交而被取消。这个细节很重要，否则"发布"会被一次普通的 push 打断。

## 七、权限最小化

```yaml
# 默认最小权限；需要额外权限的 job 各自声明。
permissions:
  contents: read

jobs:
  image:
    permissions:
      contents: read
      packages: write     # 推 GHCR 需要
  gitops:
    permissions:
      contents: write     # 需要提交回仓库
```

顶层只给 `contents: read`，两个需要的 job 各自加码。`quality` 和 `manifests` 就停在只读上——它们确实只需要读。

为什么要显式写：`GITHUB_TOKEN` 的默认权限由**仓库设置**决定，可能相当宽（比如默认 `write-all`）。显式在 workflow 里声明最小集合之后，即使有人把某个 job 改坏了、或者某个 action 被投毒去尝试别的事，它能做的也被限制在声明的范围内。

这里的设计原则是**按 job 授权，而不是按 workflow 授权**。`packages: write` 只给真正推镜像的 `image`，`contents: write` 只给真正提交的 `gitops`。反过来说，如果把它们提到顶层，那么 `quality`（跑着第三方 lint action）也会同时拥有推包和写仓库的权限。

## 八、这条流水线**没有**做的事

README 的"已知边界"里列了这些，这里说明为什么它们不该塞进这条 workflow：

| 没有的环节 | 常见做法 | 为什么不放进来 |
|---|---|---|
| 镜像漏洞扫描 | Trivy / Grype | 它是**独立的关注点**。混进来之后，job 失败的原因变得模糊——是代码坏了，还是基础镜像今天出了个新 CVE？后者和这次 commit 无关，却会红掉所有人的 PR |
| SBOM 生成 | syft / `docker buildx --sbom` | 同上；而且 SBOM 的消费方（合规、审计）和 CI 的消费方（开发者）不是同一批 |
| 镜像签名 | cosign | 签名需要**长期私钥**，而这条流水线的凭证模型（短期 `GITHUB_TOKEN`）不覆盖它。引入签名等于引入一套密钥管理，那是另一个工程 |
| 准入校验 | Kyverno / OPA Gatekeeper | 它属于**集群侧**，不属于 CI。集群有能力对"不管谁创建的" Pod 做校验；CI 只能管住自己这一条路径。本项目用 Pod Security Admission 做了最轻量的一层（见 03） |
| 渐进式发布 | 金丝雀 / 蓝绿 / 流量切分 | 它改的是"**流量怎么切**"，属于部署策略，位置在 Argo Rollouts 或 Service Mesh，不是 CI 的一个 job。放进来会让 CI 拥有流量控制能力，边界就烂了 |

判断标准可以总结成一句：**CI 的职责是"证明这批代码可以被发布"，而不是"把它发布出去"，也不是"持续运营它"。** 前者是流水线，后两者分别是 CD 和运行时的职责。

把它们分开的实际好处是**失败语义清晰**：这条流水线红了，一定是这次提交的问题。

## 九、一张对照表：本地命令 ↔ CI job

| CI job | 本地等价命令 | 差异 |
|---|---|---|
| `quality` / 检查格式 | `make fmt-check` | 同一个表达式（`gofmt -l $(git ls-files '*.go')`） |
| `quality` / go vet | `make vet` | 一致 |
| `quality` / golangci-lint | `make lint` | 版本一致（v2.12.2），二进制来源不同 |
| `quality` / 测试 | `make test` | 一致（都是 `-race -count=1`） |
| `quality` 全部 | `make check` | `make check` = fmt-check + vet + lint + test |
| `manifests` / 渲染 | `make render-dev` | CI 渲染**全部** overlay，本地一次一个 |
| `manifests` / schema 校验 | `make validate` | **不同层**：CI 用 kubeconform（离线 schema），本地用 `kubectl --dry-run=server`（真实准入） |
| `image` | `make image-multiarch` | 本地产出 OCI tar 验证构建路径，CI 推 GHCR |
| `image`（单架构） | `make image` / `make image-push-local` | 本地只建 host 架构 |
| `gitops` | *（无刻意等价物）* | 它是 CI 与 CD 的交接点，本地不该模拟。手动改 tag 用 `kustomize edit set image` |

关于 `make validate` 和 CI 的 schema 校验是**不同层**这件事，值得再说一句：CI 里没有集群，也不应该为了校验清单去连一个集群，所以用离线的 kubeconform；而本地有集群，就能做更强的服务端 dry-run。我在 03 里验证过两者的能力边界——那个拼错 container 名字的 patch，kubeconform 给出 `Valid: 5, Invalid: 0`（放过了），而 `kubectl apply --dry-run=server` 拦住了它：

```console
The Deployment "cnlab" is invalid: spec.template.spec.containers[0].image: Required value
```

所以本地开发时值得**先 `make render-dev` 看渲染结果，再 `make validate` 过服务端准入**——第二层是 CI 那条流水线覆盖不到的，因为它没有集群也不该去连一个集群。

## 小结

| job | 一句话职责 | 关键设计 |
|---|---|---|
| `quality` | 证明代码可以被构建和测试 | 工具版本锁死（Go 读 `go.mod`、lint 写死 v2.12.2） |
| `manifests` | 证明清单能渲染且字段合法 | 两层检查：`kustomize build` + `kubeconform -strict` |
| `image` | 产出可追溯的多架构镜像 | `--platform=$BUILDPLATFORM` 免 QEMU；显式计算不可变 tag |
| `gitops` | 提交新的期望状态（不部署） | `[skip ci]` + `GITHUB_TOKEN` 双保险防循环 |

三个值得记住的点：

1. **没有 deploy 是设计，不是遗漏。** CI 的边界在"提交期望状态"。
2. **能渲染 ≠ 合法，合法 ≠ 会被接受。** 三层检查各拦一类错，谁都替代不了谁。
3. **自动化的输出必须被验证。** `latest` 那次事故的根因不是工具出错，是没人核对它的输出。

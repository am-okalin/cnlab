# 踩坑记录

这里记录的是**本项目实际踩到并修掉**的坑，不是从别处抄来的常见问题清单。每一条都按「现象 → 根因 → 绕法 → 教训」写，因为最容易浪费时间的往往不是坑本身，而是**现象和根因之间那段误导性的距离**。

分成两类：

- **A 类：本机环境专有。** 来自"受限沙箱 + goenv + 非用户属主的 Homebrew"这套组合。换一台普通开发机大概率不会遇到，所以集中放在 [hack/env.sh](../hack/env.sh) 里处理。
- **B 类：通用。** 换任何机器都会踩，属于云原生交付本身的知识点。

# A 类：本机环境专有

## A1. brew 以 exit 0 结束，却什么都没装

**现象**

```bash
$ brew install kind kustomize
$ echo $?
0
$ kind version
bash: kind: command not found
```

命令成功、退出码 0、但二进制不存在。极易误判成"装好了，可能是 PATH 问题"，然后在 PATH 上白折腾。

**根因**

两个问题叠加：

1. `/opt/homebrew` 的属主不是当前用户，brew 无法在 `/opt/homebrew/bin` 建立链接；
2. Homebrew 的缓存目录 `~/Library/Caches/Homebrew` 在受限沙箱下不可写，brew 连 API 元数据都下载不了。

brew 在这两种情况下会打印警告后放弃，但退出码仍是 0。真正的错误信息被 `| tail -20` 之类的管道吃掉了。

**绕法**

完全不依赖 brew，把工具按**固定版本**装进项目内的 `bin/`：

```bash
make tools          # 等价于 ./hack/install-tools.sh
```

版本写在脚本里（kind v0.33.0、kustomize v5.8.3），带来两个额外好处：可复现、想清干净直接删目录。

如果你想把 brew 本身修好：`sudo chown -R "$(whoami)" /opt/homebrew`。

**教训**

**不要用退出码判断"工具装好了"，要用 `command -v` 或直接执行一次。**

## A2. `package net/http is not in std` —— 一个把人引向完全错误方向的报错

**现象**

```bash
$ go vet ./...
main.go:26:2: package net/http is not in std (/Users/wtn/.goenv/versions/1.25.12/src/net/http)
main.go:25:2: package log/slog is not in std (...)
```

看起来像 Go 标准库被删了。但 `ls` 那个目录，文件都在。

**根因**

goenv 的 shim 会把 `GOCACHE` 覆写成：

```
$GOROOT/go-build-<host>-<host>-cgo
```

而 `GOROOT` 位于 `~/.goenv/versions/...`，在受限沙箱下不可写。go 无法写构建缓存，于是**误报**成"包不在标准库里"。

验证：

```bash
$ env -u GOCACHE go env GOCACHE          # 走 shim
/Users/wtn/.goenv/versions/1.25.12/go-build-host-host-cgo
$ env -u GOCACHE /Users/wtn/.goenv/versions/1.25.12/bin/go env GOCACHE   # 真实的 go
/Users/wtn/Library/Caches/go-build
```

**绕法**

绕过 shim，直接调用真实二进制，并把所有缓存放进工作区。见 `hack/env.sh`：

```bash
export PATH="${CNLAB_ROOT}/bin:${PATH}"     # bin/go 是指向真实 SDK 的软链
export GOCACHE="${CNLAB_CACHE}/gocache"
export GOTMPDIR="${CNLAB_CACHE}/gotmp"
export GOPATH="${CNLAB_CACHE}/gopath"
export GOMODCACHE="${CNLAB_CACHE}/gomodcache"
```

`bin/go` 这个软链由 `hack/install-tools.sh` 创建（`$GOROOT/bin/go` 就是真实的 go）。

**教训**

**当一个报错说"标准库不存在"时，先怀疑构建缓存权限，而不是真的去检查标准库。** 编译器的错误信息描述的是它观察到的现象，不一定是你以为的原因。

## A3. golangci-lint 自己也是 goenv shim

**现象**

修好 A2 之后，`go vet` 正常了，但 lint 仍然报同一个错：

```bash
$ golangci-lint run ./...
level=error msg="[linters_context] typechecking error: open .../go-build-host-host-cgo/...: operation not permitted"
```

即使 `PATH` 里 `bin/go` 已经排在最前面也没用。

**根因**

`which golangci-lint` → `~/.goenv/shims/golangci-lint`。它也是 shim，`goenv exec` 会给它注入那个只读的 `GOCACHE`，它再把这份环境传给内部调用的 `go`。**显式设置的环境变量优先级高于 go 的默认值，所以我们在外层设的 `GOCACHE` 被 shim 覆盖了。**

**绕法**

同样软链真实二进制到 `bin/`：

```
bin/golangci-lint -> ~/.goenv/versions/1.25.12/bin/golangci-lint
```

**教训**

**"我设了环境变量"不等于"子进程收到了我设的值"。** 中间任何一层 wrapper 都可能改写它。排查这类问题要看最内层进程实际拿到的值。

## A4. kind 报建集群失败，其实集群已经建好了

**现象**

```bash
$ make kind-up
✓ Starting control-plane 🕹️
✓ Installing CNI 🔌
✓ Joining worker nodes 🚜
ERROR: failed to create cluster: failed to lock config file: open /Users/wtn/.kube/config.lock: operation not permitted
$ echo $?
1
```

看起来集群创建失败。但：

```bash
$ kind get clusters
cnlab
$ docker ps --filter label=io.x-k8s.kind.cluster
cnlab-worker          Up 40 seconds
cnlab-control-plane   Up 40 seconds
```

节点全都在跑，只是最后写 kubeconfig 那一步失败了。

**根因**

`~/.kube/config` 在沙箱下不可写。

**绕法**

把 kubeconfig 也放进项目内：

```bash
export KUBECONFIG="${CNLAB_CACHE}/kubeconfig"
```

额外好处：完全不污染你本机真实的 `~/.kube/config`，想清干净删 `.cache/` 就行。

同时 `hack/kind-up.sh` 改成**无论集群是新建还是已存在，都重新导出一次 kubeconfig**，这样"集群在、kubeconfig 丢了"的情况能自愈。

**教训**

**看到"创建失败"先 `kind get clusters` 确认实际状态。** 另外，`kind-up.sh` 这类脚本要写成幂等的，才能让"上次失败"不变成"永远失败"。

## A5. buildx 写不了自己的活动记录

**现象**

```bash
$ docker buildx build --platform linux/arm64 -t cnlab:dev --load .
ERROR: failed to build: failed to update builder last activity time: open
/Users/wtn/.docker/buildx/activity/.tmp-desktop-linux1617076902: operation not permitted
```

**根因**

buildx 会往 `~/.docker/buildx/activity/` 写活动时间戳。同属"写不进 `$HOME`"。

**绕法**

```bash
export BUILDX_CONFIG="${CNLAB_CACHE}/buildx"
```

## A6. gh CLI 写不了缓存目录

**现象**

```bash
$ gh run view --job 123 --log
failed to get run log: creating cache directory: mkdir /Users/wtn/.cache/gh: operation not permitted
```

**根因 / 绕法**

同类问题。gh 遵循 `XDG_CACHE_HOME`：

```bash
export XDG_CACHE_HOME="${CNLAB_CACHE}/xdg"
```

# B 类：通用（换机器也会踩）

## B1. kind 把宿主代理透传进节点，导致节点拉不到任何外网镜像

这是本项目**最隐蔽**的一个坑，因为它伪装成了"镜像不存在"。

**现象**

Pod 一直 `ImagePullBackOff`。kubelet 事件里是：

```
Failed to pull image "localhost:5001/cnlab:dev": failed to pull and unpack image
"localhost:5001/cnlab:dev": failed to resolve reference "localhost:5001/cnlab:dev":
failed to do request: Head "http://kind-registry:5000/v2/cnlab/manifests/dev":
proxyconnect tcp: dial tcp 127.0.0.1:10801: connect: connection refused
```

明明是我们自己接的本地仓库、镜像也 push 成功了，却拉不到。后来连 ArgoCD 的官方镜像（quay.io / ghcr.io）也全部拉不到，7 个 Pod 全是 `ImagePullBackOff`。

**根因**

两层叠加：

1. 宿主机设了 `http_proxy=http://127.0.0.1:10801`，**kind 会把这个变量原样透传进节点容器**；
2. 节点容器里的 `127.0.0.1` 是**节点自己**，不是你的 Mac。而那个代理只在 Mac 的 loopback 上监听。

于是 containerd 每次拉镜像都先去连"节点自己的 10801 端口"，必然失败。kind 会自动往 `NO_PROXY` 里追加自己的网段和节点名，但**不会加我们自定义的仓库主机名**。

**绕法**

先确认节点能不能直连（这一步是关键，它把"网络不通"和"代理配置错误"区分开了）：

```bash
docker exec cnlab-worker bash -c '
for hp in quay.io:443 ghcr.io:443 registry-1.docker.io:443; do
  host=${hp%:*}; port=${hp#*:}
  timeout 8 bash -c "exec 3<>/dev/tcp/$host/$port" 2>/dev/null \
    && echo "  $host DIRECT OK" || echo "  $host DIRECT FAIL"
done'
```

实测三个都 `DIRECT OK`，说明节点本身网络是通的，问题纯粹出在代理变量。

于是 `hack/kind-up.sh` 在创建集群时把代理摘掉：

```bash
env -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY \
  -u http_proxy -u https_proxy -u all_proxy \
  "$KIND" create cluster --config kind/cluster.yaml
```

如果你的网络确实必须经代理出网，就把 `CNLAB_NODE_PROXY` 设成一个**节点可达**的地址：

```bash
CNLAB_NODE_PROXY=http://host.docker.internal:10801 make kind-up
```

**⚠️ 最关键的一点**：代理变量是**烘进节点容器**的。集群建好之后再改宿主机的 `NO_PROXY` / 取消代理，**没有任何效果**——只能删掉集群重建。本项目在这里浪费了一轮完整的调试。

**教训**

1. **`ImagePullBackOff` 不等于"镜像不存在"。** 先看 kubelet 事件里的完整错误，它会告诉你失败在哪一层。
2. **容器里的 `localhost` 永远不是你的 `localhost`。** 这条规则适用于所有代理、回调地址、webhook 配置。
3. **kind 会透传宿主代理**，这是它有意为之的行为，但在"代理只监听 loopback"的场景下必然出事。

## B2. `net/http` 的 Shutdown 会被 StateNew 连接拖满 5 秒

**现象**

测试偶发失败：同一个测试有时 0.85s 通过，有时 5.2s 超时。日志里 `已优雅退出 grace=4.744s`——drain 只配了 800ms，`Shutdown` 却花了 4.7 秒。

**根因**

`net/http` 对处于 StateNew（TCP 已 accept、但还没读到请求字节）的连接，要等它闲置满 5 秒才关闭（`net/http` Issue 22682）。连接池复用很容易制造这种连接。

**绕法**

测试客户端关掉 keep-alive，并加一条"退出耗时应接近 DRAIN_DELAY"的回归断言。

**生产影响**

这个坑在生产同样存在且无法靠改客户端回避——**kubelet 的探针每次都会新建 TCP 连接**。所以 `terminationGracePeriodSeconds` 不能按"DRAIN_DELAY + 请求耗时"贴着算，必须留至少 5 秒余量。

详见 [探针与优雅下线](02-探针与优雅下线.md#四一个真实的坑statenew-连接让-shutdown-卡满-5-秒)。

## B3. `imagePullPolicy: IfNotPresent` + 可变 tag = "我明明推了新镜像"

**现象**

改了代码、`make image-push-local` 成功、`kubectl rollout restart` 也执行了，但 Pod 的行为还是旧的。

**根因**

镜像 tag 还是 `:dev`，节点上已经有这个 tag 了，`imagePullPolicy` 默认 `IfNotPresent`，containerd 就认为不需要重新拉取。**镜像 tag 指向的 digest 变了，但 tag 本身没变。**

**绕法**

dev overlay 显式设 `imagePullPolicy: Always`：

```yaml
# deploy/overlays/dev/patch-dev.yaml
spec:
  template:
    spec:
      containers:
        - name: cnlab
          imagePullPolicy: Always
```

生产则反过来：用不可变 tag（git sha 或语义化版本）+ `IfNotPresent`。这样既没有这个坑，又让"运行的是哪份代码"可追溯。

**教训**

**可变 tag 和 `IfNotPresent` 是一对危险的组合。** 二者只能留一个——要么用可变 tag + `Always`（dev），要么用不可变 tag + `IfNotPresent`（prod）。

## B4. 用 `kubectl port-forward` 测"零中断"，测出来的失败是假的

**现象**

第一次写零中断验证时，用本机 `curl` 打 `kubectl port-forward svc/cnlab`，滚动更新期间必然出现连接失败。看起来"优雅下线没生效"。

**根因**

`kubectl port-forward svc/cnlab` 会在建立时挑定**某一个** Pod，然后把连接固定在上面。滚动更新替换掉那个 Pod 时，port-forward 本身必然断开。**这个失败是测试方法的产物，不是服务的问题。**

**绕法**

压测必须在集群内、走 Service 进行，让 kube-proxy 按 endpoints 转发：

```bash
# hack/zero-downtime-demo.sh 里就是这么做的
kubectl -n cnlab-dev run loadgen --image=... --restart=Never -- \
  sh -c 'wget -q -O /dev/null http://cnlab.cnlab-dev.svc.cluster.local/...'
```

改完之后结果变成 **60/60 成功，fail=0**。

**教训**

**验证一个机制之前，先问"我的测量方法本身会不会引入误差"。** 一个会自己制造失败的测试，比没有测试更糟——它会让你去修一个不存在的问题。

## B5. `metadata-action` 的 `version` 输出选到了 `latest`

**现象**

CI 的 GitOps 步骤把 `staging` 的镜像 tag 写成了 `latest`：

```
chore(gitops): staging -> latest [skip ci]
```

而预期是 `sha-<commit>`。

**根因**

工作流原本这样写：

```yaml
tags: |
  type=sha,format=short,prefix=sha-
  type=ref,event=tag
  type=raw,value=latest,enable={{is_default_branch}}
```

然后用 `${{ steps.meta.outputs.version }}` 作为"要写回 git 的 tag"。但 `version` 输出是**按优先级挑一个 tag** 的结果，而 `type=raw,value=latest` 的优先级高于 `type=sha`——于是拿到的是 `latest`。

这直接破坏了整套设计的前提：用不可变 tag 才能回答"线上跑的是哪份代码"。

**绕法**

不再依赖 action 的优先级规则，自己显式计算：

```yaml
- name: 计算不可变 tag
  id: tag
  run: |
    set -euo pipefail
    if [[ "${GITHUB_REF_TYPE}" == "tag" ]]; then
      echo "value=${GITHUB_REF_NAME}" >> "$GITHUB_OUTPUT"
    else
      echo "value=sha-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"
    fi
```

修完之后，三方一致：CI 写入 `sha-f24b9a4` → ArgoCD 同步后 staging 运行
`ghcr.io/am-okalin/cnlab:sha-f24b9a4` → 应用 `/api/v1/version` 自报
`version=sha-f24b9a4`、`commit=f24b9a4e80edcb80af918e8ca06524333ae11ccf`
（`version` 是短 sha，`commit` 是完整 40 位 sha，两者指向同一个提交）。

**教训**

**自动化的输出也必须被验证。** 流水线"成功"了，不代表它做对了事。第一条 bot 提交是绿色的，但内容是错的。

## B6. `kubeconform` 需要 go >= 1.26，而 `setup-go` 默认禁止切换工具链

**现象**

CI 的清单校验 job 失败：

```
go: github.com/yannh/kubeconform/cmd/kubeconform@v0.8.0:
    github.com/yannh/kubeconform@v0.8.0 requires go >= 1.26
    (running go 1.25.12; GOTOOLCHAIN=local)
```

本地同一条命令能成功。

**根因**

`actions/setup-go` 默认设置 `GOTOOLCHAIN=local`，禁止 `go` 自动下载并使用更新的工具链。本地之所以能成功，是因为本地允许自动下载。

这是最经典的"本地过、CI 挂"——差异不在代码，在于**本地和 CI 对工具链切换的策略不同**。

**绕法**

改用官方预编译二进制，彻底不依赖宿主 Go：

```bash
KUBECONFORM_VERSION=v0.8.0
curl -sSL --retry 3 -o /tmp/kubeconform.tar.gz \
  "https://github.com/yannh/kubeconform/releases/download/${KUBECONFORM_VERSION}/kubeconform-linux-amd64.tar.gz"
tar -xzf /tmp/kubeconform.tar.gz -C /tmp kubeconform
```

**教训**

**CI 里尽量用预编译二进制，而不是 `go install`。** 后者会把"CI 的 Go 版本/工具链策略"变成你的隐性依赖。

## B7. `[[ ... ]] && cmd` 作为脚本最后一条语句会让脚本以非零码退出

**现象**

`hack/install-tools.sh` 末尾有一行：

```bash
[[ -x "$BIN/golangci-lint" ]] && "$BIN/golangci-lint" --version
```

在 CI 上 `bin/golangci-lint` 不存在（CI 用官方 action 提供 linter），这行会返回 1。

**根因**

实测行为（`set -e` 下）：

```bash
# 后面还有别的语句 → 不中断，脚本最终 exit 0
$ bash -c 'set -e; [[ -x /nonexistent ]] && echo hi; echo 后续语句执行了'; echo $?
后续语句执行了
0

# 作为最后一条语句 → 脚本以 exit 1 结束
$ bash -c 'set -e; echo start; [[ -x /nonexistent ]] && echo hi'; echo $?
start
1
```

本项目当时侥幸没出事，因为这行后面还有 `echo`。但这是个定时炸弹。

**绕法**

写成显式的 `if`：

```bash
if [[ -x "$BIN/golangci-lint" ]]; then
  "$BIN/golangci-lint" --version
fi
```

**教训**

**`A && B` 单独成句时，A 为假会让整个语句非零。** 在 `set -e` 脚本里要把它写成 `if`，或者确保后面还有别的语句兜底——后者是靠运气。

# 一条元教训

把这 13 条放在一起看，会发现**大部分时间不是花在"解决问题"上，而是花在"识别现象和根因之间的误导性距离"上**：

- A1：退出码说成功，实际什么都没做
- A2：报错说标准库不存在，实际是缓存写不进去
- A4：报错说创建失败，实际集群已经建好
- B1：报错说镜像拉不到，实际是代理不可达
- B4：测试说服务有中断，实际是测法有问题
- B5：流水线说成功，实际输出是错的

所以本项目在写每一环时都尽量做到**可自证**：

- 镜像里带 `version` / `commit` / `buildTime`，运行时可以用 `/api/v1/version` 自报身份（B5 就是靠这个被发现和验证的）
- 优雅下线的每一步都打日志，能被断言（B2、B4）
- 清单渲染结果可以被 diff（不部署也能看）
- `make validate` 用真实集群做服务端 dry-run

**能被观测到的东西，才谈得上被验证。**

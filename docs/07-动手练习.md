# 动手练习

这份文档里的每一条练习都对应一个**具体的故障现象**。不是"配置项说明书"，而是"把这个配置改坏，看它怎么坏，然后你就再也不会配错了"。

练习按难度分三档，但难度和重要性无关——入门里的三条比挑战里的五条更常用。**先把入门和进阶做完再往下走**，因为挑战里的每一条都建立在前面的机制上。

---

## 怎么用这份文档

**前置**：先确认基础环境是通的。

```bash
make tools && make kind-up && make image-push-local && make deploy-dev && make smoke
make zero-downtime    # 期望：60/60 成功，fail=0
```

**观察脚手架**：三条命令覆盖了 90% 的场景，先设个别名省事。

```bash
alias k='kubectl --context kind-cnlab'

k -n cnlab-dev get pod -w                              # 看就绪状态与重启次数
k -n cnlab-dev logs -l app.kubernetes.io/name=cnlab -f --tail=50
k -n cnlab-dev get events --field-selector reason=Unhealthy --sort-by=.lastTimestamp
```

关于 `-w`：`READY` 那一列（`1/1`）反映的是 readinessProbe，`RESTARTS` 那一列反映的是 livenessProbe 或进程退出。**这两个数字分别对应两种探针，这是所有探针练习的观察入口。**

**重置纪律**：练习改的都是 `deploy/overlays/*` 或集群里的对象。每条练习末尾给了还原方式，通用还原是：

```bash
git checkout -- deploy/ gitops/
make deploy-dev
```

涉及 ArgoCD 的练习（2.2 / 2.3 / 3.5）需要先跑过：

```bash
make argo-install && make argo-bootstrap && make argo-status
```

**一个必须提前知道的交互**：dev 的 Application 开着 `automated.selfHeal`。这意味着一旦 ArgoCD 在跑，你在工作区改完直接 `make deploy-dev`，**几秒内就会被纠回 git 里的状态**。做 1.x / 2.1 / 2.5 这类"本地改、本地看"的练习时，如果发现改动莫名其妙自己变回去了，先看 `make argo-status`——不是你的问题，是 selfHeal 在工作。想干净地做实验，就先按 2.3 的办法把 dev 的 automated 关掉。

# 入门

## 1.1 READY_DELAY、三种探针，以及一个被简化过的说法

### 目标

把"存活"和"就绪"这两个词从概念变成你能看见的两个数字：`READY` 列和 `RESTARTS` 列。同时搞清楚 `startupProbe` 到底在管什么。

### 准备

编辑 `deploy/overlays/dev/kustomization.yaml`，在 `configMapGenerator` 的 `literals` 里加一行 `READY_DELAY`：

```yaml
configMapGenerator:
  - name: cnlab-config
    behavior: merge
    literals:
      - APP_ENV=dev
      - LOG_LEVEL=debug
      - DRAIN_DELAY=3s
      - SHUTDOWN_TIMEOUT=10s
      - GREETING=hello-from-dev
      - READY_DELAY=20s        # ← 新增
```

`READY_DELAY` 是应用认识的变量（`main.go` 的 `loadConfig`），但当前三套 overlay 里**都没有设置它**，所以走的是默认值 `0s`。加进去之后：

```bash
make render-dev | grep -A3 'kind: ConfigMap'    # 确认 ConfigMap 名字的哈希后缀变了
make deploy-dev
kubectl --context kind-cnlab -n cnlab-dev rollout status deploy/cnlab --timeout=120s
```

### 阶段 A：观察现象

在另一个终端：

```bash
kubectl --context kind-cnlab -n cnlab-dev get pod -w
```

**预期现象**：

- 新 Pod 立刻进入 `Running`，但 `READY` 一直是 `0/1`
- 大约 20 秒后变成 `1/1`，同一时刻 `rollout status` 才返回成功
- **`RESTARTS` 始终是 0**
- 事件里能看到反复的 `Startup probe failed: HTTP probe failed with statuscode: 503`
  （注意是 **startupProbe** 在报错，不是 readiness —— 在 startupProbe 通过之前，
  liveness 和 readiness 根本不会执行，这正是 startupProbe 的核心语义）
- 日志里能看到 `等待预热完成 ready_delay=20s`，20 秒后是 `已就绪，开始接收流量`

### 阶段 B：为什么会这样——三种探针的分工

看 `deploy/base/deployment.yaml` 里三个探针实际打的是哪个端点，这是理解一切的钥匙：

| 探针 | 打到 | 失败后果 | 在这次实验里的表现 |
|---|---|---|---|
| `startupProbe` | `/readyz` | 重启容器（但在它通过前，另两个探针被挂起） | 预热期内持续失败，把 liveness 隔离在启动期之外 |
| `livenessProbe` | `/healthz` | 重启容器 | 永远成功，`RESTARTS` 保持 0 |
| `readinessProbe` | `/readyz` | **只摘流量，不重启** | 20 秒内一直 503 |

而 `main.go` 里这两个端点的语义是严格分开的：

- `handleHealthz` 无条件返回 200，只报告 `uptime`。它**从进程开始监听的那一刻就是 200**，和预热、和下游依赖全都无关。
- `handleReadyz` 在 `a.ready` 为 false 时返回 503。`a.ready` 在 `READY_DELAY` 走完之前是 false，在收到 SIGTERM 之后又被置回 false。

所以这次实验的结论是：**只有 readiness 会因为"还没准备好"而变化；liveness 只会因为"进程出了问题"而变化。** 这就是为什么 `/healthz` 绝不该去 ping 数据库——它一失败，kubelet 就开始杀容器，一次依赖抖动会被放大成"所有 Pod 连环重启"。

### 阶段 C：这两句话曾经是错的（本练习最值得带走的一段）

README 的环境变量表里原本写着：

> `READY_DELAY` | `0s` | 人为延迟就绪。调到 20s 可以观察 startupProbe 的价值

`main.go` 的 `run()` 里也有对应的注释：

> `READY_DELAY` 用来演示 startupProbe —— 把它调到 20s，你会看到没有 startupProbe 时容器被 livenessProbe 反复杀掉。

**在本项目最初提交的版本里，这两句话都不成立。** 而这个练习正是发现它的过程：

- `livenessProbe` 打的是 `/healthz`，与 `READY_DELAY` 完全无关，永远返回 200。所以把 `READY_DELAY` 设成 20s，Pod 只是 `0/1` 停 20 秒，**RESTARTS 保持 0**。
- 更隐蔽的是 `startupProbe` 当时**也**打 `/healthz`：于是第一次探测（约 2s）就通过，`failureThreshold: 30` 那个"60 秒启动预算"在实际运行中**一次都用不到**。清单渲染正常、Pod 正常启动、不报任何错——它只是"证明了 startupProbe 存在"，并没有在保护慢启动。

这类错误查不出来，只能靠对照实验发现，也正是下面阶段 D / E 存在的理由。

**两处说法都已经修正**：README 的环境变量表改成了"只影响 `/readyz`"，`main.go` 的注释也改成了准确表述，并且 `startupProbe` 的端点从 `/healthz` 改成了 `/readyz`。你手上的版本是对的，但这一段保留了当时的判断过程——因为**"注释写了一个不成立的行为"这件事本身，比那个行为更值得记住。**

### 阶段 D：制造真正的探针误用

```bash
kubectl --context kind-cnlab -n cnlab-dev patch deploy cnlab --type=json -p \
  '[{"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/httpGet/path","value":"/readyz"}]'

kubectl --context kind-cnlab -n cnlab-dev get pod -w
```

**预期现象**：`RESTARTS` 开始以约 30 秒的间隔递增（`periodSeconds: 10` × `failureThreshold: 3`），日志里反复出现「等待预热完成」，进程永远到不了"稳定就绪"。

**原理**：这就是把"依赖状态"或"预热状态"塞进 liveness 的后果。容器每次重启，`READY_DELAY` 的计时都从头开始，于是永远在"刚起来就被杀"的循环里。生产上这个模式的表现是 `CrashLoopBackOff`，而根因（探针打错了端点）通常被误诊成"应用启动有问题"。

还原：

```bash
kubectl --context kind-cnlab -n cnlab-dev patch deploy cnlab --type=json -p \
  '[{"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/httpGet/path","value":"/healthz"}]'
```

### 阶段 E：startupProbe 的真实价值

`startupProbe` 的意义不是"防止 liveness 杀容器"这么简单，而是**让"启动慢"和"运行中卡死"可以用两套独立的阈值表达**。要看到它的价值，得让 liveness 检查的东西在启动期确实不可用：

1. 保持 `livenessProbe` 打 `/readyz`（阶段 D 的误用状态）
2. 把 `READY_DELAY` 调到 `90s`
3. 删掉 `startupProbe`（编辑 `deploy/base/deployment.yaml`）→ 观察：容器每 30 秒被杀一次，**永远起不来**
4. 加回 `startupProbe`，但把它的 `httpGet.path` 改成 `/readyz`、`failureThreshold: 30`（`2s × 30 = 60s` 预算）→ 观察：仍然起不来，但**被杀的间隔从 30 秒变成了 60 秒**
5. 把 `READY_DELAY` 降到 `40s`（低于 60s 预算）→ 观察：这次起来了，`RESTARTS` 保持 0

第 4 步和第 5 步才是 `startupProbe` 真正买到的东西：**它把"启动期"这段特殊时间从 liveness 的判据里隔离出去，并给这段隔离期单独设一个预算。**

本项目实测的对照数据（`READY_DELAY=45s`，liveness 打 `/readyz`）：

| startupProbe | RESTARTS 变化 | 能否就绪 |
|---|---|---|
| 无 | 40s → 1，80s → 2，100s → 3 | **永远不能** |
| 有，打 `/readyz` | 恒为 0 | 45s 后正常就绪 |

项目的 `startupProbe` 现在打的已经是 `/readyz`。把这个练习完整做一遍，你会对"探针打错端点不会报错、只会在真实压力下暴露"这件事有具体的体感——这比记住三个探针的定义有用得多。

### 还原

```bash
git checkout -- deploy/
make deploy-dev
```

## 1.2 DRAIN_DELAY=0：把 502 变出来

### 目标

搞清楚 `DRAIN_DELAY` 到底在保护什么。这条练习是所有练习里最重要的一条——因为它解释的是"滚动更新为什么能不中断"。

### 操作

编辑 `deploy/overlays/dev/kustomization.yaml`，把 `DRAIN_DELAY=3s` 改成 `DRAIN_DELAY=0s`：

```bash
make deploy-dev
kubectl --context kind-cnlab -n cnlab-dev rollout status deploy/cnlab --timeout=180s
make zero-downtime
```

`make zero-downtime` 会：先故意提交一个以 root 运行的 Pod 让 Pod Security Admission 拒绝它（`cnlab-dev` 标了 `pod-security.kubernetes.io/enforce: restricted`），然后启动一个合规的压测 Pod 走 **Service** 连续打 60 个请求（其中 1/3 是 `?d=300ms` 的慢请求），在压测进行中 `rollout restart`，最后打印结果。

**压测必须走 Service 而不是 `kubectl port-forward`**：port-forward 会把连接固定在当时选中的某一个 Pod 上，滚动更新替换掉那个 Pod 时连接必然断开——这样测出来的失败是测试方法的产物。只有经过 kube-proxy 按 endpoints 转发，才真的验证了"就绪探针 → endpoints 摘除 → 优雅下线"这条链路。

### 预期现象

- 压测输出那一行变成 `RESULT total=60 ok=<60> fail=<非零>`
- 中间会穿插 `FAILED request #N`
- 被替换 Pod 的日志里仍然有前两行，但 drain 窗口是 0：

  ```
  收到终止信号，开始优雅下线
  就绪探针已置为失败，等待流量摘除 drain_delay=0s
  已优雅退出 grace=0s
  ```

对照基线：`DRAIN_DELAY=3s` 时实测是 `60/60` 成功、`fail=0`，被替换 Pod 的完整日志是「收到终止信号」→「就绪探针已置为失败，等待流量摘除 drain_delay=3s」→「已优雅退出 grace=0s」。

> `fail` 的具体数字每次都会不同——它是一个**概率性故障**，取决于 endpoints 传播有多快、压测当时打到第几个请求。如果某次跑出来 `fail=0`，别急着下结论，`make zero-downtime` 连跑三次再看。这个"不稳定复现"本身就是它危险的原因：这种问题在测试环境大概率测不出来，上线后偶发，然后被归到"网络抖动"。

### 原理：Shutdown 保护不了什么

`main.go` 的优雅下线是三步，顺序不能换：

```go
a.ready.Store(false)                     // 1. 立刻让 /readyz 失败，把自己从 endpoints 摘出去
// 等 DRAIN_DELAY                        // 2. 等摘除动作在集群内传播完成
srv.Shutdown(shutdownCtx)                // 3. 关监听器，等在途请求自然返回
```

关键认知：**`srv.Shutdown` 能保护的只是"已经在处理中的请求"，它保护不了"还在往这个 Pod 新建连接"的请求。**

Pod 被删除时，K8s 会并发地做两件事：从 Service 的 endpoints 里摘除它，给容器发 SIGTERM。而 endpoints 的变更要经过 EndpointSlice 更新、kube-proxy 改写 iptables/ipvs 规则，才能在每个节点上生效。

- `DRAIN_DELAY > 0`：进程在这段时间里**还在正常服务**（只是不再接受新流量），于是"规则还没更新完"那几秒里被转发过来的连接照样能处理完。
- `DRAIN_DELAY = 0`：进程在毫秒内退出监听，而 kube-proxy 还在往它转发连接 → 新连接被拒 → 用户看到 502。

所以那一步 `a.ready.Store(false)` 不是装饰：**它让"摘流量"这个动作由应用主动发起，而不是等 kubelet 的探针周期把它算成 NotReady。** 顺便说，kubelet 发现 `/readyz` 变 503 还需要 `periodSeconds × failureThreshold = 3s × 2 = 6s`，这也是为什么 `DRAIN_DELAY` 需要留够余量——它覆盖的是"从应用已经不想收流量"到"集群真的不再发流量"之间那段谁都不负责的时间。

### 还原

```bash
git checkout -- deploy/
make deploy-dev
```

## 1.3 terminationGracePeriodSeconds 小于 DRAIN_DELAY：让「已优雅退出」消失

### 目标

亲眼看到两个**互不知情**的计时器（kubelet 的宽限期、应用的 drain 窗口）没对齐时的现象，并记住这个现象长什么样——生产上它出现的时候，没人会想到是时间预算问题。

### 操作（快速版，不改清单）

```bash
POD=$(kubectl --context kind-cnlab -n cnlab-dev get pod -l app.kubernetes.io/name=cnlab \
        -o jsonpath='{.items[0].metadata.name}')
echo "$POD"

# Pod 删掉之后 kubectl logs 就读不到了，所以先把日志流抓进文件
kubectl --context kind-cnlab -n cnlab-dev logs -f "$POD" > /tmp/old-pod.log 2>&1 &
sleep 1

# 把这次的宽限期压到 1 秒（dev 的 DRAIN_DELAY 是 3s）
kubectl --context kind-cnlab -n cnlab-dev delete pod "$POD" --grace-period=1

sleep 3
grep -E '终止信号|摘除|优雅退出|就绪' /tmp/old-pod.log
```

### 预期现象

日志到此为止：

```
收到终止信号，开始优雅下线
就绪探针已置为失败，等待流量摘除 drain_delay=3s
```

**没有「已优雅退出」那一行。** 而且 Pod 在约 1 秒后就消失了，而不是 3 秒。

想看到退出码，在删除的同时另开一个终端：

```bash
kubectl --context kind-cnlab -n cnlab-dev get pod "$POD" -w \
  -o jsonpath='{.status.containerStatuses[*].lastState.terminated.exitCode}{"\n"}'
```

预期能看到 `137`（128 + 9，即 SIGKILL）。这个观察有竞态，抓不到就算了——日志里缺那一行已经是足够明确的证据。

### 操作（清单版，更接近真实）

`terminationGracePeriodSeconds` 是 Pod 级字段。编辑 `deploy/overlays/dev/patch-dev.yaml`：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cnlab
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 1     # ← 新增，故意小于 DRAIN_DELAY=3s
      containers:
        - name: cnlab
          imagePullPolicy: Always
```

```bash
make deploy-dev
kubectl --context kind-cnlab -n cnlab-dev rollout status deploy/cnlab --timeout=120s
# 先等这批 grace=1s 的 Pod 起来，再做第二次滚动更新，被替换的才是它们
kubectl --context kind-cnlab -n cnlab-dev rollout restart deploy/cnlab
kubectl --context kind-cnlab -n cnlab-dev rollout status  deploy/cnlab --timeout=120s
```

注意这里必须做两步：`make deploy-dev` 之后被删除的是**旧的 grace=30s 的 Pod**（K8s 用 Pod 自身的 spec 里那个值），只有等新一批 `grace=1s` 的 Pod 起来之后，第二次 `rollout restart` 才是在测你想测的东西。这条"改了 Pod 级字段要等一轮滚动更新才生效"的规律，在排查这类问题时经常被忽略。

### 原理

两个计时器完全独立，而且**不通信**：

| 计时器 | 谁在数 | 从什么时候开始 | 到点做什么 |
|---|---|---|---|
| `terminationGracePeriodSeconds` | kubelet | 发出 SIGTERM 的瞬间 | `SIGKILL`，容器硬死 |
| `DRAIN_DELAY` + `SHUTDOWN_TIMEOUT` | 应用 | 收到 SIGTERM 的瞬间 | 关闭监听器，等在途请求 |

只要 `grace < DRAIN_DELAY + 最长请求耗时 + 余量`，应用就一定拿不到"把话说完"的机会。当前的配置是：

| 环境 | DRAIN_DELAY | SHUTDOWN_TIMEOUT | terminationGracePeriodSeconds | 余量 |
|---|---|---|---|---|
| dev | 3s | 10s | 30s | 17s |
| staging | 5s | 15s | 30s | 10s |
| prod | 10s | 20s | 45s | 15s |

（staging 用的是 base 的 `terminationGracePeriodSeconds: 30`；prod 由 `deploy/overlays/prod/patch-prod.yaml` 提到 45s。）

真实项目里这个预算几乎总是被破，因为改这两个值的通常是两个人：改 `DRAIN_DELAY` 的人在调应用，改 `terminationGracePeriodSeconds` 的人在调清单。所以 README 把它写成了一条必须对齐的公式，而不是一个注释。

**为什么不能靠 `preStop: sleep N` 来回避这件事**：`deploy/base/deployment.yaml` 里专门解释了本项目为什么没有 `preStop`。两个原因——一是它在容器里白等 N 秒（distroless 里连 `sleep` 都没有），而且这 N 秒和 `terminationGracePeriodSeconds` 是**双重计时**，会让总时间变得难以推算；二是更根本的，正确做法应该由应用自己表达，而"应用能不能优雅退出"是可分离、可观测、可测试的（见 `main_test.go` 里的 `TestGracefulShutdownDrainsInFlight`）。`preStop sleep` 是"因为应用不会优雅退出，所以在外面糊一层"的补偿。

```bash
make deploy-dev
```

## 2.1 用 ConfigMap 变更触发滚动更新

### 目标

看懂 `configMapGenerator` 的哈希后缀，以及它为什么等价于"改配置自动重启"。然后把它关掉，体会关掉之后会发生什么。

### 操作

```bash
# 1. 记下当前的名字
make render-dev | grep -A3 'kind: ConfigMap'
#    预期看到类似：name: cnlab-config-h6k4tb279k

# 2. 改一个值：deploy/overlays/dev/kustomization.yaml 里
#      - GREETING=hello-from-dev
#    改成
#      - GREETING=hello-from-v2

# 3. 看哈希变了没有
make render-dev | grep -A3 'kind: ConfigMap'

# 4. 看差异里到底有几处变化
make diff-dev

# 5. 应用
make deploy-dev
kubectl --context kind-cnlab -n cnlab-dev rollout status deploy/cnlab
make smoke        # 看 /api/v1/greet 的 message
```

### 预期现象

- ConfigMap 的名字从 `cnlab-config-h6k4tb279k` 变成 `cnlab-config-<另一个哈希>`
- `make diff-dev` 里同时出现三件事：新 ConfigMap 被创建、旧 ConfigMap 被删除、**Deployment 的 `envFrom.configMapRef.name` 被改写**
- 滚动更新被**自动**触发，不需要 `rollout restart`
- `/api/v1/greet?name=cnlab` 返回 `hello-from-v2, cnlab!`

这一步和 1.2 的区别值得对照着看：**改 ConfigMap 不需要 `rollout restart`，改代码需要。** 因为前者改变了清单（Pod 模板里的引用名变了），后者没有（镜像地址 `:dev` 没变）。

### 原理

`deploy/base/kustomization.yaml` 里显式写着 `generatorOptions.disableNameSuffixHash: false`。这个开关让 kustomize：

1. 用 ConfigMap 的内容算一个短哈希
2. 把哈希追加到名字后面
3. 把所有引用 `cnlab-config` 的地方改写成带哈希的名字

于是"改配置"在 K8s 眼里就变成了"Pod 模板引用的对象名变了"→ Pod 模板哈希变了 → 滚动更新。**这就是"配置变更自动生效"的全部机制，没有别的魔法。**

现在把它关掉：

```yaml
generatorOptions:
  disableNameSuffixHash: true
```

再做一遍同样的修改，你会看到：ConfigMap 内容变了、名字没变、Pod 模板没变、**什么都没发生**。已有的 Pod 甚至不会重新读环境变量——环境变量是在进程启动时读进内存的。这时候唯一的办法是 `kubectl rollout restart`。

这个坑在生产里的典型现象是："我在 ConfigMap 里把日志级别改成 debug 了，为什么没生效？"——因为没生效是**正确行为**，生效才需要额外动作。

代价也要知道：哈希后缀意味着每次改一个字都产生一个新的 ConfigMap 对象。dev 环境无所谓；如果某个环境的配置变更很频繁且 ConfigMap 体积很大（比如塞了一份 nginx.conf），对象数量和 etcd 压力都会涨。这时候的做法是把频繁变动的配置改成挂载卷（`volumes` + `configMap`），让 kubelet 去同步文件——但那条路有自己的坑（同步延迟最长约 1 分钟，且进程要自己 watch 文件变化）。

### ⚠️ 和 ArgoCD 的冲突

如果你已经装了 ArgoCD 并且 dev 的 Application 在自动同步，第 5 步 `make deploy-dev` 之后，ArgoCD 会在几秒内把 Deployment 的 `envFrom` 纠回 git 里那个旧哈希（见 2.2）。新哈希的 ConfigMap 不在 ArgoCD 的追踪范围内，**可能作为孤儿留在命名空间里**。

做这条练习时，要么先按 2.3 的办法关掉 dev 的 automated，要么干脆把改动 push 上去让 ArgoCD 自己同步。做完检查一下有没有留下垃圾：

```bash
kubectl --context kind-cnlab -n cnlab-dev get cm
```

```bash
git checkout -- deploy/
make deploy-dev
```

## 2.2 制造漂移，观察 selfHeal

### 目标

看清 `selfHeal` 的语义，以及"手动改集群"在这套体系下意味着什么。

### 操作

```bash
# 终端 1
kubectl --context kind-cnlab -n cnlab-dev get deploy cnlab -w

# 终端 2
kubectl --context kind-cnlab -n cnlab-dev scale deploy/cnlab --replicas=3
make argo-status
```

### 预期现象

几秒内（实测约 4 秒）副本数被改回 1。`make argo-status` 里 `cnlab-dev` 的状态会短暂地经过 `OutOfSync` 然后回到 `Synced`——通常快到看不清，因为纠偏是事件驱动的。

### 关掉 selfHeal 做对比

```bash
# 只关 selfHeal，保留 prune
kubectl --context kind-cnlab -n argocd patch application cnlab-dev --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":{"selfHeal":false}}}}'

kubectl --context kind-cnlab -n cnlab-dev scale deploy/cnlab --replicas=3
kubectl --context kind-cnlab -n cnlab-dev get deploy cnlab        # 一直是 3
make argo-status                                                   # OutOfSync，但 ArgoCD 不动手
```

**预期现象**：副本数稳定停在 3，`make argo-status` 里 `SYNC STATUS` 一直是 `OutOfSync`。ArgoCD **仍然在比对**，只是**不动手**。

还原：

```bash
kubectl --context kind-cnlab -n argocd patch application cnlab-dev --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":{"selfHeal":true}}}}'
# 关掉 automated 期间产生的漂移不会自动消失，手工收一下
kubectl --context kind-cnlab -n cnlab-dev scale deploy/cnlab --replicas=1
```

### 原理

`selfHeal` 的语义是"**live 状态一旦偏离目标状态，就让它回到目标状态**"，不是"定期重置"。4 秒这个量级来自集群内的 watch 事件路径，**和 git 轮询无关**——ArgoCD 默认的 `timeout.reconciliation` 是 3 分钟，那是针对 git 变更的。

`automated` 只有两个开关，它们的语义完全不同：

| 开关 | 管什么 | 关掉之后 |
|---|---|---|
| `selfHeal` | live 偏离了怎么办 | 漂移可见，但不纠正 |
| `prune` | git 里删掉的资源怎么办 | 只做加法，集群里的孤儿资源永远留着 |

所以 `automated.prune: false, selfHeal: true` 这个组合是有意义的：手动改动会被纠正回来，但**删资源必须由人来做**。`gitops/examples/cnlab-prod.yaml` 里把这条写成了给生产的折中建议。

**为什么生产不能无脑开 selfHeal + prune**：

- 应急时运维手动 `scale`、改镜像、加副本——几秒后被抹掉，故障还在。
- `gitops/bootstrap/root-app.yaml` 里有一条针对本项目写死的警告：**每个 overlay 都包含自己的 Namespace 对象，而 Namespace 被删除时里面的所有东西会跟着消失。** 开着 prune 的前提下，"顺手把 `deploy/overlays/dev/namespace.yaml` 删掉再 push"等于删掉 `cnlab-dev` 里的一切。

## 2.3 给 staging 关掉 automated，体验人工 Sync 与 Diff

### 目标

亲手走一遍"生产应该有的形态"：ArgoCD 持续告诉你哪里不一致，但绝不替你决定。

### 操作

```bash
# 1. 确认当前是自动同步
kubectl --context kind-cnlab -n argocd get application cnlab-staging -o yaml | grep -A6 syncPolicy

# 2. 整段摘掉 automated
kubectl --context kind-cnlab -n argocd patch application cnlab-staging --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":null}}}'

# 3. 制造一个差异：直接在集群里改，不动 git
kubectl --context kind-cnlab -n cnlab-staging scale deploy/cnlab --replicas=4

# 4. 看状态与 diff
make argo-status
kubectl --context kind-cnlab -n argocd get application cnlab-staging \
  -o jsonpath='sync={.status.sync.status} health={.status.health.status}{"\n"}'
```

### 预期现象

- `sync=OutOfSync`，但 staging 的副本数稳定停在 4 —— **ArgoCD 一次都没有动手**
- 打开 UI（`make argo-ui`，`https://localhost:8443`，用户 `admin`，密码见 `make argo-password`）点进 `cnlab-staging` → `DIFF`，能看到 `spec.replicas: 4` vs `2` 的高亮差异

### 人工触发同步

```bash
kubectl --context kind-cnlab -n argocd patch application cnlab-staging --type=merge \
  -p '{"operation":{"initiatedBy":{"username":"admin"},"sync":{"revision":"main"}}}'

kubectl --context kind-cnlab -n cnlab-staging get deploy cnlab -w    # 回到 2
```

**预期现象**：副本数被拉回 2，状态回到 `Synced`，`operation` 字段在状态里留下一条同步记录（谁触发的、同步到哪个 revision）。

### 原理

`automated` 整段不存在时，ArgoCD 退化成"只读监察者"：它仍然持续 diff、仍然在 UI 上把差异标红、仍然报告 health——**但它绝不 write**。这就是 `gitops/examples/cnlab-prod.yaml` 选择的形态：**可见性自动化，变更人工化**。

`gitops/examples/cnlab-prod.yaml` 顶部的注释把取舍说得比任何二手资料都清楚：

> 自动同步 + prune 的组合意味着一次错误的合并可以无声地把生产资源删掉。人工确认这个环节不是官僚主义，它是在"快"和"可挽回"之间做选择。

注意 prod 那个文件**刻意放在 `examples/` 而不是 `apps/`**。因为 `gitops/bootstrap/root-app.yaml` 用 `directory.recurse: true` 扫描 `apps/` 目录，放进去就等于自动启用了。

### 还原

```bash
kubectl --context kind-cnlab -n argocd patch application cnlab-staging --type=merge \
  -p '{"spec":{"syncPolicy":{"automated":{"prune":true,"selfHeal":true}}}}'
```

## 2.4 prod 的副本数与 PDB：让 `kubectl drain` 卡住

### 目标

看到 PDB 在"自愿中断"时真的会拦住排空，并理解为什么它既是护栏也可能是枷锁。

### 准备

prod overlay 用的是 `ghcr.io/am-okalin/cnlab:v0.1.0`，本练习环境里这个 tag 很可能不存在（CI 只推过 `sha-f24b9a4`）。所以先把镜像地址替换成本地的 dev 镜像再应用——注意 **Makefile 里只有 `deploy-dev` 和 `deploy-staging`，没有 `deploy-prod`**，这一步得手敲：

```bash
export PATH="$PWD/bin:$PATH"
source hack/env.sh

kustomize build deploy/overlays/prod \
  | sed 's#ghcr.io/am-okalin/cnlab:v0.1.0#localhost:5001/cnlab:dev#' \
  | kubectl --context kind-cnlab apply -f -

kubectl --context kind-cnlab -n cnlab-prod get deploy,po,pdb -o wide
```

（`sed` 只是让练习跑得起来。真实环境里这个替换应该走 overlay，不该用管道。）

### 操作

```bash
# 1. 看 PDB 当前允许几个中断
kubectl --context kind-cnlab -n cnlab-prod get pdb cnlab -o wide
#    NAME    MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS
#    cnlab   2               N/A               1

# 2. 找唯一的 worker 节点（control-plane 有 NoSchedule 污点，Pod 调度不上去）
kubectl --context kind-cnlab get nodes
NODE=$(kubectl --context kind-cnlab get nodes -l '!node-role.kubernetes.io/control-plane' \
         -o jsonpath='{.items[0].metadata.name}')
echo "$NODE"

# 3. 排空它
kubectl --context kind-cnlab drain "$NODE" --ignore-daemonsets --delete-emptydir-data --timeout=60s
```

同时在另一个终端：

```bash
kubectl --context kind-cnlab -n cnlab-prod get pdb cnlab -w
kubectl --context kind-cnlab -n cnlab-prod get pod -o wide -w
```

### 预期现象

1. 第 1 个 cnlab Pod 被成功驱逐，`ALLOWED DISRUPTIONS` 从 `1` 变成 `0`
2. 第 2 个驱逐请求被拒，drain 反复重试并打印：

   ```
   error when evicting pods/"cnlab-xxxx" -n "cnlab-prod" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget.
   ```

3. 60 秒后 drain 失败退出：`error: unable to drain node ... context deadline exceeded`
4. 被驱逐的那个 Pod 一直 `Pending` —— 因为节点已经被 cordon，而集群只有一个 worker

### 原理

**PDB 只拦"自愿中断"。** `kubectl drain` 走的是 Eviction API，属于自愿中断，所以被拦；节点宕机、`OOMKilled`、探针触发的重启属于非自愿中断，PDB 完全不管。所以 **PDB 不是可用性保证，而是"别让运维操作自己把服务搞挂"的护栏**。

拦截的算法很直接：

```
disruptionsAllowed = 当前可用副本数 - minAvailable
```

3 副本 + `minAvailable: 2` → 只允许同时驱逐 1 个。驱逐第 1 个之后它变成 Terminating/NotReady，可用数落到 2，`disruptionsAllowed` 归 0，第 2 个就被拒。这就是"为了保证可用性配了 PDB，结果运维连节点都换不了"的真实故障，也是 `pdb.yaml` 里写"经验值是 `minAvailable = 副本数 - 1`"的原因——如果设成 `minAvailable: 3`，任何 Pod 都驱逐不了，drain 会**立刻**卡死，一个都走不掉。

单节点集群里这条练习必然卡死；要让它能走完，需要至少 2 个 worker，让被驱逐的 Pod 有地方重建。

### ⚠️ 必须收尾

```bash
kubectl --context kind-cnlab uncordon "$NODE"
kubectl --context kind-cnlab delete namespace cnlab-prod
```

不 `uncordon` 的话，你的单节点集群会一直处于"不可调度"状态，后面所有练习的 Pod 都会 Pending。

## 2.5 加一个新的环境 overlay

### 目标

算清"加一个环境"的真实成本，以及成本落在哪一层。

### 操作

```bash
cp -r deploy/overlays/dev deploy/overlays/qa
```

然后改三处：

```yaml
# deploy/overlays/qa/namespace.yaml
metadata:
  name: cnlab-qa              # 原来是 cnlab-dev

# deploy/overlays/qa/kustomization.yaml
namespace: cnlab-qa           # 原来是 cnlab-dev
configMapGenerator:
  - name: cnlab-config
    behavior: merge
    literals:
      - APP_ENV=qa             # 原来是 dev
      # 其余 literals 保持
labels:
  - pairs:
      app.kubernetes.io/environment: qa   # 原来是 dev

# deploy/overlays/qa/patch-dev.yaml —— 建议改名成 patch-qa.yaml，并同步改 kustomization 里的 patches.path
```

验证渲染和 schema 校验：

```bash
export PATH="$PWD/bin:$PATH"
source hack/env.sh

kustomize build deploy/overlays/qa | grep -E '^kind:|^  namespace:'
kustomize build deploy/overlays/qa | kubectl --context kind-cnlab apply --dry-run=server -f -
```

### 预期现象

- 渲染出 5 个资源（Namespace / ServiceAccount / ConfigMap / Service / Deployment），全部带 `namespace: cnlab-qa`
- 服务端 dry-run 通过
- **集群里什么都不会发生**——qa 没有对应的 ArgoCD Application

### 原理与两个值得注意的点

**1. 完整的"加环境"动作是四个文件，而且集群侧零操作。**

`gitops/bootstrap/root-app.yaml` 用 `directory.recurse: true` 扫描 `gitops/apps/`。所以真正完整的动作是：加 overlay（3 个文件）+ 加 `gitops/apps/cnlab-qa.yaml` + push。之后 `cnlab-root` 会自己把新的 Application 同步出来。**这就是 app-of-apps 的杠杆：加环境不需要碰集群。**

**2. 但同一套机制带着刀。**

`root-app` 开着 `prune: true`，而每个 overlay 里都包含自己的 Namespace 对象。**删掉 `deploy/overlays/qa/namespace.yaml` 再 push，等于删掉 `cnlab-qa` 命名空间和里面的一切。** 这条警告就写在 `root-app.yaml` 里。

**3. 一个本地/CI 覆盖面不一致的地方。**

CI 的 `manifests` job 用的是 glob：

```bash
for dir in deploy/overlays/*/; do ... kustomize build "$dir" ... done
```

所以新增的 `qa` overlay **会被 CI 校验**。但 `make validate` 目标是写死的：

```make
for o in dev staging prod; do ...
```

所以 `make validate` **不会校验 `qa`**。本地和 CI 的覆盖范围不一致，意味着你本地"验过了"而 CI 仍然可能红。要么把 `make validate` 也改成 `deploy/overlays/*/`，要么记得手动加上新环境。

**4. 成本账。**

加一个环境 = 3~4 个文件。但如果环境间的差异继续变大（不同的探针参数、不同的 Service 类型、不同的资源上限、不同的 HPA 阈值），overlay 会越长越像一份完整清单。这时候的判断标准是：

> **如果 overlay 里超过一半的字段都在重复 base 的内容，说明切分位置选错了。**

往下的两条路是：把可复用的差异抽成 kustomize `components/`，或者换 Helm（values 天然是多维的）。Kustomize 的优势是"差异被显式列举、diff 干净"，Helm 的优势是"参数可以组合、可以给别人当库用"。环境数超过三四个、且差异开始呈组合爆炸时，Kustomize 的收益就反转了。

### 还原

```bash
rm -rf deploy/overlays/qa
```

## 3.1 可观测性栈：把 `/metrics` 接进 Prometheus + Grafana

### 目标

让 `/metrics` 从"一段能 curl 的文本"变成"能回答 p99 是多少"的图表。

### 现状

`main.go` 里的 `/metrics` 是手写的 Prometheus 文本格式，指标名以 `cnlab_` 为前缀，包含 `cnlab_build_info`、`cnlab_ready`、`cnlab_http_requests_total`、`cnlab_http_request_duration_seconds`（直方图）、`go_goroutines` 等。但三套 overlay 里**没有任何 Prometheus 相关的东西**——没有 ServiceMonitor，Pod 模板上也没有 `prometheus.io/scrape` 注解。所以这完全是"从零加"。

### 操作

```bash
# 1. 装 helm（沿用项目惯例：进 bin/，不用 brew）
HELM_VERSION=v3.16.0      # 换成你需要的版本；写死版本是为了可复现
curl -fsSL -o /tmp/helm.tar.gz \
  "https://get.helm.sh/helm-${HELM_VERSION}-darwin-arm64.tar.gz"
tar -xzf /tmp/helm.tar.gz -C /tmp
mv /tmp/darwin-arm64/helm bin/helm
export PATH="$PWD/bin:$PATH"; source hack/env.sh
helm version

# 2. 装 kube-prometheus-stack
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm -n monitoring upgrade --install kps prometheus-community/kube-prometheus-stack \
  --create-namespace \
  --set alertmanager.enabled=false \
  --set prometheus.prometheusSpec.resources.requests.memory=256Mi \
  --set prometheus.prometheusSpec.resources.limits.memory=512Mi \
  --set grafana.resources.requests.memory=128Mi
```

> ⚠️ 如果 Docker 只分了 4GB 内存（`kind/cluster.yaml` 里写着这台机器的实际情况），这一步大概率会把整个集群压到 OOM。**先把 Docker Desktop 内存调到 8GB 以上**，这也是 README 给出的建议。调完不需要重建 kind 集群，但 ArgoCD 和 Prometheus 同时跑仍然会很紧张——做完把没用的卸掉。

```bash
# 3. 让 Prometheus 抓 cnlab
kubectl --context kind-cnlab -n cnlab-dev apply -f - <<'EOF'
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: cnlab
  namespace: cnlab-dev
  labels:
    release: kps                    # 必须匹配 Helm release 名，否则 Prometheus 不会选中它
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: cnlab # 选中 Service
  namespaceSelector:
    matchNames: [cnlab-dev]
  endpoints:
    - port: http                    # Service 的端口名，不是 8080
      path: /metrics
      interval: 15s
EOF
```

```bash
# 4. 看抓取是否成功
kubectl --context kind-cnlab -n monitoring port-forward svc/kps-kube-prometheus-prometheus 9090:9090 &
# 浏览器打开 http://localhost:9090/targets
#   → 应该出现 serviceMonitor/cnlab-dev/cnlab/0，State = UP

# Grafana
kubectl --context kind-cnlab -n monitoring get secret kps-grafana \
  -o jsonpath='{.data.admin-password}' | base64 -d; echo
kubectl --context kind-cnlab -n monitoring port-forward svc/kps-grafana 3000:80
```

### 预期现象

- Targets 页面出现 `serviceMonitor/cnlab-dev/cnlab/0`，`State = UP`，`Labels` 里带着 Pod 名
- 在 Prometheus 的 Query 里查下面三条，都能出数：

  ```
  sum(rate(cnlab_http_requests_total[1m])) by (route)
  histogram_quantile(0.99, sum(rate(cnlab_http_request_duration_seconds_bucket[5m])) by (le))
  cnlab_ready
  ```

- 把 dev 副本扩到 2 后，`cnlab_build_info` 的 series 数从 1 变成 2：

  ```
  count(cnlab_build_info)
  ```

### 原理

**Prometheus 不认识你的应用。** 它只是在按固定周期抓一段约定格式的文本。`/metrics` 里 `# TYPE` 之后的行才有语义，而没有 `# TYPE` 声明的指标 Prometheus 会直接忽略。

抓取对象是 **Service**（ServiceMonitor 选 Service，再由 Endpoints 展开成"每个 Pod 一个 target"），所以服务发现走的是 K8s API，而不是手写 `static_configs`。

`main.go` 里那套手写指标的两个真实约束会在这里现形：

1. **标签基数**。`observe` 中间件用的是 `r.Pattern`（路由模板，形如 `GET /api/v1/greet` 去掉方法后剩 `/api/v1/greet`），不是 `r.URL.Path`。所以 `?name=alice` 和 `?name=bob` 只产生**一条**时间序列。`main_test.go` 里有一条断言专门守这件事：

   ```go
   greetSeries := strings.Count(got.body, `cnlab_http_requests_total{method="GET",route="/api/v1/greet"`)
   if greetSeries != 1 { t.Errorf("greet 路由产生了 %d 条序列, 期望 1（标签基数泄漏）", greetSeries) }
   ```

   如果换成 `r.URL.Path`，一个带用户 ID 的路径就能把内存打爆。这是 Prometheus 使用者最常翻的车。

2. **直方图必须有 `+Inf` 桶**。缺了它，Prometheus 会**整个指标**拒绝，而不是只丢一条。

还有两个容易忽略的地方：

- **就绪状态顺带决定了可观测性覆盖面。** ServiceMonitor 通过 Endpoints 发现 target，而 Endpoints 里只有**就绪**的 Pod。所以 Pod 没就绪时 Prometheus 根本抓不到它——`cnlab_ready 0` 这个值你永远不会在 Prometheus 里看到（因为它就是那个抓不到的状态）。想解耦，就把指标端口单独开一个（并在 Service 上加第二个端口），或者用 metadata-only 的抓取方式。
- **⚠️ ArgoCD 会把你的 ServiceMonitor 删掉。** 你手工 `kubectl apply` 的 ServiceMonitor 在 `cnlab-dev` 里，而 dev 的 Application 开着 `prune: true`。正确做法是把它写进 `deploy/overlays/dev/` 目录并 push，让 git 成为它的来源。

### 卸载

```bash
helm -n monitoring uninstall kps
kubectl --context kind-cnlab delete namespace monitoring
kubectl --context kind-cnlab -n cnlab-dev delete servicemonitor cnlab --ignore-not-found
```

## 3.2 渐进式发布：Argo Rollouts 金丝雀 10% → 50% → 100%

### 目标

把"一次性滚动替换"换成"先给一小部分流量，观察，再逐步放大"，并亲眼看到**没有真正的流量路由器时，权重只是一个近似值**。

### 操作

```bash
# 1. 装 Argo Rollouts（版本按 https://github.com/argoproj/argo-rollouts/releases 的最新稳定版替换）
ARGO_ROLLOUTS_VERSION=<填入实际版本>
kubectl --context kind-cnlab create namespace argo-rollouts
kubectl --context kind-cnlab apply -n argo-rollouts -f \
  "https://github.com/argoproj/argo-rollouts/releases/download/${ARGO_ROLLOUTS_VERSION}/install.yaml"
kubectl --context kind-cnlab -n argo-rollouts rollout status deploy/argo-rollouts
```

```bash
# 2. 用一个新的命名空间做实验，不碰 dev
kubectl --context kind-cnlab create namespace cnlab-canary
```

写一个 Rollout。**容器 spec 直接抄 `deploy/overlays/dev` 渲染结果里的 `containers` 段**——探针、resources、securityContext 一个都不能省，因为 `cnlab-dev` 之外还要给新命名空间打上 `restricted` 的 PSA 标签：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: cnlab
  namespace: cnlab-canary
spec:
  replicas: 4                     # 注意：4 副本下最小粒度是 25%，见下面"原理"
  selector:
    matchLabels:
      app.kubernetes.io/name: cnlab
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: {duration: 30s}
        - setWeight: 50
        - pause: {}               # 无限期暂停，等人点 Promote
        - setWeight: 100
  template:
    metadata:
      labels:
        app.kubernetes.io/name: cnlab
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 65532
        runAsGroup: 65532
        seccompProfile: {type: RuntimeDefault}
      containers:
        - name: cnlab
          image: localhost:5001/cnlab:dev
          ports: [{name: http, containerPort: 8080}]
          envFrom: [{configMapRef: {name: cnlab-config}}]
          # ...探针 / resources / securityContext 照抄 dev 的渲染结果...
```

```bash
kubectl --context kind-cnlab -n cnlab-canary apply -f rollout.yaml
```

```bash
# 3. 触发一次金丝雀：改一行环境变量或换一个 tag，然后观察
kubectl --context kind-cnlab -n cnlab-canary set env rollout/cnlab APP_ENV=canary

kubectl --context kind-cnlab -n cnlab-canary get rollout cnlab -w
# 装了 kubectl-argo-rollouts 插件的话：
# kubectl argo rollouts get rollout cnlab -n cnlab-canary --watch
# 没有插件时看状态字段：
kubectl --context kind-cnlab -n cnlab-canary get rollout cnlab \
  -o jsonpath='step={.status.currentStepIndex} weight={.status.canary.weights.canary.weight} stable={.status.replicas}{"\n"}'
```

### 预期现象

- Rollout 在 `setWeight: 10` 之后**实际起了 1 个金丝雀 Pod**，而不是 0.4 个
- 达到 `pause: {}` 时状态停在 `Paused`，`status.currentStepIndex` 停住，需要显式继续：

  ```bash
  # 有插件
  kubectl argo rollouts promote cnlab -n cnlab-canary
  # 没插件：改 spec 里的 steps 或直接 patch 掉暂停（不推荐，仅演示）
  ```

- 期间把 Service 指向它，用 `make zero-downtime` 那套压测逻辑观察失败率

### 原理

**没有 `trafficRouting` 时，`setWeight` 是靠副本数比例近似实现的。** 这是最需要理解的一点：

- 不配 Istio / NGINX Ingress / Gateway API 时，Argo Rollouts 无法改写流量规则。它只能控制"金丝雀 Pod 占多少个"，再依赖 Service 把请求随机分给所有后端 Pod。
- 所以**能表达的最小权重 = 1 / replicas**。4 副本下 `setWeight: 10` 实际是 1 个 Pod ≈ 25%。
- 想看到接近 10% 的流量比例，要么把副本数提到 10 以上（本机 4GB 内存不现实），要么接一个真正的流量路由器。

**权重是这样近似的，也正是它能工作的原因**：`deploy/base/service.yaml` 的 selector 是 `app.kubernetes.io/name: cnlab`，金丝雀 Pod 和稳定 Pod 用同一个标签，所以两者都在同一个 Service 后面。这让"按副本数近似"成立，也让它无法精确控制权重。

**ArgoCD 的配合**：ArgoCD 内置了 `argoproj.io/Rollout` 的健康检查（`resource_customizations` 里的 `health.lua`），所以把 Rollout 放进 overlay 后，UI 上会显示 `Progressing` / `Healthy` / `Paused`，而不是 `Unknown`。如果显示 `Unknown`，说明你的 ArgoCD 版本太老。本项目 `hack/argo-install.sh` 固定了 `ARGOCD_VERSION`，改动前先确认一下。

**最后一点，也是最容易被忽略的**：金丝雀发布的有效性完全取决于**你能多快发现金丝雀是坏的**。没有 3.1 那套指标，金丝雀就只是一个"多等 30 秒再全量"的仪式。**先做 3.1，再做 3.2。**

### 卸载

```bash
kubectl --context kind-cnlab delete namespace cnlab-canary argo-rollouts
```

## 3.3 供应链安全：Trivy 扫描 + SBOM + cosign 签名 + 准入校验

### 目标

把"这个镜像能不能进集群"从"靠人 review"变成"一条可执行的策略"。

### 四层，从便宜到贵

#### 第 1 层：CI 里扫描 + 把扫描变成闸门

在 `.github/workflows/ci.yml` 的 `image` job 之后加一个 job：

```yaml
  scan:
    name: 镜像扫描
    runs-on: ubuntu-latest
    needs: image
    permissions:
      contents: read
      packages: read
    steps:
      - uses: aquasecurity/trivy-action@<版本>
        with:
          image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ needs.image.outputs.tag }}
          format: table
          severity: HIGH,CRITICAL
          ignore-unfixed: true
          exit-code: '1'
```

然后改依赖关系，**让 `gitops` 依赖 `scan`**：

```yaml
  gitops:
    needs: [image, scan]
```

这一步的顺序设计才是重点。为什么闸门要卡在 `gitops` 而不是 `image`：

- 推镜像（`image` job）和让集群部署它（`gitops` job 写回 tag）是**两件事**。镜像进了 registry 不等于有人会部署它。
- 本项目里"什么会被部署"完全由 `deploy/overlays/staging/kustomization.yaml` 里的 tag 决定。所以**扫描失败时不写这个文件，坏镜像就永远部署不出去**——不需要回滚，不需要删镜像。
- 想把坏镜像彻底挡在 registry 之外，就得让 `image` job 先 `load: true` 到 runner 本地、扫完再 push。代价是多一次镜像搬运。

**为什么现在扫意义有限**：`gcr.io/distroless/static-debian12:nonroot` 这个基础层只有 14.1MB，里面几乎没有可扫的东西——这正是选它的理由。**真正需要盯的是你开始引入第三方依赖之后。** 这条练习的价值在于"先把闸门装上"，而不是"现在扫出了什么"。

#### 第 2 层：SBOM（生成并归档）

```yaml
      - uses: anchore/sbom-action@<版本>
        with:
          image: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ needs.image.outputs.tag }}
          format: spdx-json
          output-file: sbom.spdx.json
      - uses: actions/upload-artifact@v4
        with: {name: sbom, path: sbom.spdx.json}
```

SBOM 的作用不是"扫描"，而是**在漏洞爆出来的时候，能立刻回答"我们哪个镜像里有这个包"**。没有 SBOM，你就得把所有镜像重新拉下来重新扫一遍；有 SBOM，你查文本就行。

#### 第 3 层：cosign 签名（keyless）

```yaml
      - uses: sigstore/cosign-installer@<版本>
      - run: cosign sign --yes \
          ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}@${{ needs.image.outputs.digest }}
```

两个要点：

- **签的是 `digest`，不是 tag。** tag 是可变的（`image` job 里 `latest` 就在被反复覆盖）。签名绑在 tag 上等于没签——攻击者推一个同名 tag 就能顶掉。`ci.yml` 里已经为这个准备好了 `image` job 的 `outputs.digest`。
- **keyless 模式靠 GitHub OIDC**，不需要在仓库里存一把长期私钥。代价是验证时必须能访问 Fulcio/Rekor 的信任根（TUF），这在离线环境里会成为一个新问题。

#### 第 4 层：准入校验（唯一真正能拦住的一层）

用 Kyverno 或 sigstore policy-controller，规则大意是"这个命名空间里的镜像必须能通过本仓库 workflow 的身份验证"。

**为什么必须有这一层**：CI 里的扫描是"**防自己**"——防的是你自己的代码引入漏洞。准入校验是"**防所有人**"——包括绕过 CI 直接 `docker push` 的人、包括任何能改 git 的人。

本项目里最具体的攻击面就在这句话里：

> `deploy/overlays/*/kustomization.yaml` 里的 `images.newName` 是一个纯文本字段。任何能改 git 的人，都能让集群去拉任意仓库的任意镜像。

准入校验是唯一能在这层兜住的机制。

**上线顺序**：先给 dev 用 `audit`（只记不拦）跑一段时间，确认真实流量没有误报，再切 `enforce`。直接 enforce 会把 ArgoCD 自己、kube-system 的系统镜像一起拦下来，集群会当场瘫掉。

### 预期现象

先制造一个"坏"的期望状态：

```bash
# 把 staging 的镜像换成一个不存在的仓库并 push
# deploy/overlays/staging/kustomization.yaml: newName -> ghcr.io/am-okalin/nonexistent
make argo-status
kubectl --context kind-cnlab -n cnlab-staging get pod -w
```

- 没有准入校验时：Pod 停在 `ImagePullBackOff`，事件里是 `failed to resolve reference` / `not found`
- 有准入校验时：Pod **根本不会被创建**，事件里是 webhook 的拒绝信息（`failed policy check`）

这个对比就是四层里"前三层是建议、第四层是强制"的证明。

### 本练习环境的现实限制

kind 单节点 + 4GB 内存下，Kyverno（还要带 cosign 验证链和 TUF 根）会明显吃内存。做完务必卸掉，并检查节点是否还有 Pending Pod。

## 3.4 Secret 管理：Sealed Secrets / External Secrets

### 目标

搞清楚"密文进 git"这件事的三种做法各自的代价落在哪。

### 现状

这个项目**一个 Secret 都没有**。配置全部走 ConfigMap：

```bash
grep -rn 'Secret\|secretGenerator' deploy/ gitops/ || echo "没有任何 Secret"
```

这不是疏漏，而是有意的——`GREETING` 这种值本来就该是 ConfigMap。但真实项目一定会有 `DB_PASSWORD`、`API_TOKEN` 这类东西，所以这条练习是**从零加**。

### 三条路的取舍

| 方案 | 密文进 git | 真相在哪 | 主要代价 |
|---|---|---|---|
| Sealed Secrets | 是 | 集群里的一把私钥 | **私钥备份**。丢了等于所有密文作废，且要重新加密一切 |
| External Secrets Operator | 否（只进引用） | Vault / AWS SM / GCP SM | **故障域扩大**：外部系统挂了，新 Pod 起不来（已有 Pod 不受影响） |
| SOPS + age | 是 | git | **解密密钥在 CI 和每个开发者机器上**，比 Sealed Secrets 更分散 |

### 操作（Sealed Secrets 最短路径）

```bash
# 1. 装 controller（版本按 releases 页替换）
SEALED_SECRETS_VERSION=<填入实际版本>
kubectl --context kind-cnlab apply -f \
  "https://github.com/bitnami-labs/sealed-secrets/releases/download/${SEALED_SECRETS_VERSION}/controller.yaml"
kubectl --context kind-cnlab -n kube-system rollout status deploy/sealed-secrets-controller

# 2. 装 kubeseal 客户端（进 bin/）
curl -fsSL -o bin/kubeseal \
  "https://github.com/bitnami-labs/sealed-secrets/releases/download/${SEALED_SECRETS_VERSION}/kubeseal-<os>-<arch>"
chmod +x bin/kubeseal
export PATH="$PWD/bin:$PATH"; source hack/env.sh

# 3. 取公钥
kubeseal --fetch-cert --controller-namespace kube-system > pub.pem

# 4. 把明文 Secret 加密成可以进 git 的 SealedSecret
kubectl -n cnlab-dev create secret generic cnlab-secret \
  --from-literal=API_TOKEN=demo-value-not-real \
  --dry-run=client -o yaml \
  | kubeseal --cert pub.pem --format yaml > deploy/overlays/dev/sealed-secret.yaml

cat deploy/overlays/dev/sealed-secret.yaml   # 确认 encryptedData 里是密文
```

然后：

```yaml
# deploy/overlays/dev/kustomization.yaml
resources:
  - namespace.yaml
  - sealed-secret.yaml     # ← 新增
  - ../../base
```

```yaml
# deploy/base/deployment.yaml 的容器里，给 cnlab 加一个 secretRef
          envFrom:
            - configMapRef:
                name: cnlab-config
            - secretRef:
                name: cnlab-secret      # ← 新增
```

### 预期现象

- `grep API_TOKEN deploy/` 只能找到密文，找不到明文
- 集群里出现一个 `SealedSecret` 对象和一个由它解密出来的 `Secret`：

  ```bash
  kubectl --context kind-cnlab -n cnlab-dev get sealedsecret,secret cnlab-secret
  kubectl --context kind-cnlab -n cnlab-dev get secret cnlab-secret -o jsonpath='{.data.API_TOKEN}' | base64 -d; echo
  ```

- 试着把 `sealed-secret.yaml` 的 `metadata.namespace` 从 `cnlab-dev` 改成 `cnlab-staging` 再 apply → **解密失败**，controller 日志里报无法解密

### 原理：两个必须知道的性质

**1. SealedSecret 是"命名空间 + 名字"绑定的。** 换命名空间或改名必须重新加密，否则解密失败。这经常被骂成"不能复用"，但它是**有意设计**的：它防止有人把一个环境的密文直接搬到另一个环境（比如把 prod 的密文塞进 dev 的命名空间去读出来）。

**2. SealedSecret 解密出来的 Secret 在集群里是明文。** 任何能 `kubectl get secret` 的人都读得到。它解决的是"**密文能不能进 git**"，**不是**"集群里谁能不能读"。要后者得靠 RBAC 限制 `get secret`，以及开启 etcd 的静态加密（否则 Secret 在 etcd 里也是明文存储的）。

这两条一摆出来，"选哪个方案"就变成了一组明确的问题：

- 你的解密密钥放在哪？谁能拿到？丢了怎么办？
- 你的外部依赖挂了，会不会影响 Pod 重建？（External Secrets 的答案是"会"）
- 你的审计要求是"密文可以进 git"还是"密文绝不能进 git"？

**顺带说 Kustomize 的 `secretGenerator`**：它可以生成 Secret，但生成出来的 `data` 是 base64，**不是加密**。base64 只是编码，`base64 -d` 一行就还原。别把 `secretGenerator` 当成 Secret 管理方案——它只管"怎么把一份明文塞进清单"，不管"这份明文会不会被别人看到"。

## 3.5 用 ArgoCD Image Updater / webhook 替代"CI 提交 tag"

### 目标

把 [交付链路总览](01-交付链路总览.md) 里描述的"外循环"改造成另一种形状，并说清每一次改造换来了什么、失去了什么。

### 现状回顾

当前的外循环是：CI 跑完质量门和构建，**CI 自己**把新 tag 写回 `deploy/overlays/staging/kustomization.yaml` 并 push。这要求 `gitops` job 有 `contents: write`。

### 方案 A：ArgoCD Image Updater

```bash
kubectl --context kind-cnlab apply -n argocd -f \
  https://raw.githubusercontent.com/argoproj-labs/argocd-image-updater/stable/manifests/install.yaml
kubectl --context kind-cnlab -n argocd rollout status deploy/argocd-image-updater
```

给 staging 的 Application 打注解：

```yaml
metadata:
  annotations:
    argocd-image-updater.argoproj.io/image-list: cnlab=ghcr.io/am-okalin/cnlab
    argocd-image-updater.argoproj.io/cnlab.update-strategy: newest-build
    argocd-image-updater.argoproj.io/write-back-method: git
    argocd-image-updater.argoproj.io/git-branch: main
```

两种 `write-back-method` 的差别是这条练习的核心：

- `git`：Image Updater 往 git 提交一次。审计链还在，**但「决定上哪个 tag」的主体从流水线变成了集群里的一个 controller**。
- `argocd`：直接改 Application 的 parameter override，无需 git 写权限。**但 git 不再是唯一真相来源**——override 不在 git 里，于是"集群里跑的是什么"无法再只从 git 推导出来。GitOps 的前提被破了。

### 方案 B：ArgoCD webhook（注意：这解决的是另一个问题）

很多人把"webhook"和"替代 CI 提交 tag"混为一谈，它们是两件不同的事：

- ArgoCD 的 webhook 是**入站**的：GitHub 在 push 后回调 ArgoCD，让它**立刻**去比对，而不是等默认 3 分钟的轮询。
- 它解决的是**迟滞**（"我 push 了为什么 3 分钟才同步"），**不解决"谁来写 tag"**。

所以 webhook 和"CI 提交 tag"是**互补**关系，不是替代关系。想验证的话：

```bash
kubectl --context kind-cnlab -n argocd get svc argocd-server -o jsonpath='{.spec.ports[*].name}{"\n"}'
# 然后在 GitHub 仓库 Settings → Webhooks 里加：
#   Payload URL: https://<ArgoCD 公网可达地址>/api/webhook
#   Content type: application/json
# 本机 kind 需要先有公网可达地址（ngrok / cloudflared），否则这条只能停在"知道了"。
```

### 观察

```bash
kubectl --context kind-cnlab -n argocd logs deploy/argocd-image-updater -f
kubectl --context kind-cnlab -n argocd get application cnlab-staging \
  -o jsonpath='{.status.sync.revision}{"\n"}'
git log --oneline -5      # 看提交者是 github-actions[bot] 还是 argocd-image-updater
```

### 取舍对照

| 维度 | CI 提交 tag（现状） | Image Updater |
|---|---|---|
| CI 需要的权限 | `contents: write` | 不需要写 git（`argocd` 模式） |
| git 是否唯一真相 | 是 | `git` 模式是；`argocd` 模式**不是** |
| 环境晋升语义 | 天然支持：staging 和 prod 是两个文件，各写各的 tag | 需要额外规则；默认按 registry 最新，容易把同一个 tag 同时推给多环境 |
| 凭证位置 | GHCR 推送凭证在 CI（短期 `GITHUB_TOKEN`） | registry 的**拉取**凭证要在集群里 |
| 谁决定上哪个版本 | 流水线：可审计，且质量门在它前面 | 集群里的一个 controller |
| 回滚 | `git revert` 那个 commit | `git` 模式可以；`argocd` 模式要回去改 override |
| 失败模式 | CI 挂了 → workflow 变红，期望状态不变 | Updater 挂了 → **什么都不会发生，只是版本停在原地** |

最后一行是这类"把决定权交给后台组件"的通用代价，值得单独强调：**CI 失败是响的，controller 失败是哑的。** 你会以为一切正常，直到某天发现 staging 已经三周没更新过。要装 Image Updater，就得同时给它配上"多久没更新就告警"的监控——而这又回到了 3.1。

### 一个容易被忽略的细节

`update-strategy: newest-build` 是按镜像的**构建时间**挑选最新，而不是按"CI 认定了哪个 sha"。在多个 workflow、多个分支都可能往同一个 registry 写 tag 的情况下，它会挑到"时间最新但未必是你想发布的那一个"。要收紧，就得用 `semver` 策略、或者配 `allow-tags` 正则，把选择范围限定在你能解释的集合里。
